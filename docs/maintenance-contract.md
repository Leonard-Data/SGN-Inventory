# Property maintenance contract — issue #7

Implementation in forward migration `20261011055126_property_maintenance_history.sql`; not yet hosted staging acceptance. Ordinary changes publish immediately, not through record approval. Existing reservations/rentals retain their independent authorization and row-lock rules.

## Transactional maintenance

All active employees create via `create_property(p_mode text,p_facts jsonb,p_address jsonb) → uuid`. A nonblank legacy/current known address is mandatory, optional facts may remain null, current district fields are rejected. New stable `SGN-` codes are generated independently of location/creator; imported/existing codes are immutable. Property, address and any recorded asking-price history commit together or roll back.

`maintain_property(p_property_id uuid,p_target text,p_target_id uuid|null,p_expected_revision uuid,p_changes jsonb,p_property_revision uuid,p_explanation text default null) → uuid` supports `property`, `address`, `mapping`, `contact`, `link`. The trailing explanation is the optional retained correction note: it is accepted only for a `property` change that includes `sale_price_vnd` or `monthly_rent_vnd`, must be 10–2000 characters, and is attached only to the history rows that call just inserted for that property (`xmin` of the current transaction), so a concurrent or pre-existing event can never acquire it. A non-price target, a too-short note, or a call that records no price change is refused with `23514` rather than silently dropping the note. The correction-application path attaches its outcome reason the same way and enforces the same 10–2000 bound, refusing an over-2000 raw reason and storing the trimmed note (forward migration `20261014003834_bounded_correction_outcome_reason.sql`). Use the freshly read entity UUID revision and parent property UUID revision; null target for a new address/link uses the parent revision as both. `PT409` means stale context/entity: fetch current information and explicitly reconcile, never silently retry or merge. The stale code is deliberately not `40001`, because PostgREST retries transactions failing with that serialization code, which would time stale saves out behind the maintenance gate instead of returning the conflict; forward migration `20261011125329_stale_edit_conflict_code.sql` replaced that code in the four affected functions without changing any other definition. Direct authenticated/service-role writes to the replaced tables are revoked and invoker triggers deny bypasses; public wrappers are invokers over fixed-search-path, explicitly granted private definers with live membership/role checks.

Sales edit their own unarchived property/address; staff/manager/admin maintain shared unarchived inventory. Existing reviewer-only legal/review/archive authority and active-rental guards are retained; the UI/correction workflow does not expose legal/review/archive changes. Ordinary sold transitions/reversal are excluded in favor of the independently owned sale workflow: the `23514` refusal states that ordinary maintenance does not confirm or reverse sales and names the independent sale transition (issue #32), which issue #38 delivers as the sale completion ([database-contract.md](database-contract.md#issue-38--independently-confirmed-sale-completion-and-completed-sale-ranking)); no competing status rollback/date fields are added. Subsequent business changes clear obsolete record-review certification to pending without making it a publication gate.

Property changes accept the existing typed ordinary fields. Money is a canonical whole-VND decimal string with at most 18 digits, dimensions are decimal strings with at most two fractional digits, counts are integer strings. The recorded map point is the `latitude`/`longitude` pair, which a change set must always name together; its meaning and the both-or-neither rule are owned by the [property location decision](database-contract.md#confirmed-property-contact-and-address-maintenance-decisions). Database constraints retain enum/range/nullability meaning; no float conversion or source rewriting.

## Address evidence

Legacy source contents are immutable even for owner-side writes. Correction accepts every stored format the schema allows, including an existing `alternate` row; the creation path still accepts only `legacy`/`current`, so no maintenance path creates `alternate` (forward migration `20261011190000_maintenance_alternate_creation_guard.sql`). Correct an address by inserting a successor (`supersedes_address_id`) and retain its original. Substantive current-address correction also inserts a successor and clears the superseded/current obsolete verified designation atomically. Primary replacement retains preceding rows, with at most one primary per format. A primary-only selection updates that row without discarding valid mapping evidence. Nonprimary historical records remain searchable.

Raw current addresses with no catalog match remain unresolved and usable. Current addresses contain no district. `mapping` requires manager/admin, a valid province→commune version hierarchy/effective date, supported verification method, HTTP(S) source URL and meaningful property-level `mapping_evidence`. `official_whole_mapping` additionally requires a reviewed whole/rename crosswalk; partial transitions are not substituted automatically. The same manager may designate their own address; no second approver. Unrelated prices/contacts do not invalidate address mapping.

## Shared identities and local links

`create_contact(p_changes jsonb) → uuid` requires staff/manager/admin. Creating, replacing or removing a property contact link (`maintain_property(...,'link',...)`) requires staff/manager/admin too.

`contact_impact(p_contact_id uuid) → {revision,properties:[{id,property_code}]}` requires any live employee (staff/manager/admin for an unlinked identity) and complete affected-property read authority, matching the shared-contact detail-edit permission. Show this impact before correcting a shared identity; changed membership invalidates the contact revision/preview. It is also the read the People → Contacts detail surface runs before it presents a recorded identity, so the directory cannot disclose an affected property the caller may not read.

`list_contacts(p_query text,p_after_id uuid,p_owners_only boolean,p_limit integer) → {id,display_name,contact_type,phones,raw_phone_text,revision,links:[{property_id,property_code,relation,is_primary,archived}]}` is the issue #71 directory read: an invoker wrapper over the caller's own RLS, so only identities and property relationships the caller may read are returned. Each link states its property's archived flag, so a reviewer keeps a readable archived link while the directory's stated count uses only the unarchived links — the same boundary the inventory contact filter applies. It is one ascending `id` keyset page; the wrapper returns one lookahead row so the application can offer a following page and exposes at most 30. The name query matches only a literal contiguous fragment of `display_name` — `%`, `_` and `\` are ordinary characters, matching is name-only and accent-sensitive, and a fragment longer than 120 characters returns no rows (the route refuses it first). `p_owners_only` keeps only identities with at least one readable recorded `relation='owner'` link, never the identity's `contact_type`. Every live employee reads it; creation, link changes and the correction rules above are unchanged by it.

Correcting the details of an existing linked shared contact runs through `private.maintain_contact(p_contact_id uuid,p_expected_revision uuid,p_changes jsonb) → uuid`, extracted (issue #70) from the property maintenance contact branch. It has two callers, both supplied by invoker wrappers over that one guarded function: the property-scoped `maintain_property(...,'contact',...)`, and (issue #71) the contact-scoped `maintain_contact(p_contact_id,p_expected_revision,p_changes)` the shared-contact directory uses. A directory-origin save supplies no parent property and none is invented for it: the affected set, the readable boundary and the revision all come from the shared identity itself. Every active employee may use it on a readable property, independent of property-fact edit authority, and an ordinary active employee's target must be linked to that opened property when the save came from a property; the opened property still supplies the readable-parent boundary and the parent revision check. It keeps the allowlist/bound/type validation, the transaction gate, the non-staff link requirement at the shared boundary, deterministic affected-property-before-contact locking, the contact and affected-set revision check and the affected-set archived read boundary. It appends no property history row: a contact correction changes the shared person only. Both the affected-set archived boundary and the unlinked-identity preview refusal use the additive `PT403` code (HTTP 403), while a missing live membership stays `42501`; the application maps `PT403` to `contact-refusal` and shows an inline localized refusal that names both causes and keeps the page and its current state, and maps `42501` to `access-denied` as before. Staff/manager/admin may correct an unlinked identity through the same boundary (the settled ticket #72 scope choice); property facts, addresses, mapping, link changes and creation are not widened by analogy.

Contact identity fields: `display_name`, `phones` string array, `raw_phone_text`, `contact_type`, `notes`. Preserve source phone spelling. Link fields: `contact_id`, `relation`, `is_primary`; `{remove:true}` unlinks only that property relationship. Wrong-person replacement changes the local link, not shared identity. One primary contact per property is maintained atomically. No merge/deduplication/deletion.

Maintenance uses a transaction-scoped advisory gate before parent row locks, then parent→target locks. This deliberately serializes short maintenance transactions in the single-company MVP to protect contact membership previews/fan-out and multi-parent ordering. Reservation/rental/file locks remain parent-first and otherwise unchanged. Real independent-session races are still required acceptance; embedded single-session tests do not prove them.

## Property business history

`property_history` is SELECT-only under live membership plus the property read RLS boundary (including archived reviewer restrictions). Columns: `id`, `property_id`, `actor_id`, `actor_name` snapshot, authoritative `occurred_at`, `target`, `target_id`, `changed_fields`, `before_values`, `after_values`, nullable `explanation` for a correction application. Only a recorded asking-price change adds a row (forward migration `20261015152812_property_price_only_history.sql`): a missing value and a JSON null are the same unknown, so a creation that merely leaves the price unknown records nothing, and the recorded row carries the changed asking-price fields alone. Creation, address, contact, link, note, primary-marker and status changes are no longer recorded here; they are instead attributed in the private audit trail (`private.audit_events`), which carries the actor, time and before/after values for the audited tables they write, subject to that trail's own 90-day retention window — deliberately not the permanent record `property_history` would have been. Rows recorded before that rule are retained and stay readable; nothing was rewritten or deleted. Explanation annotation is restricted to newly inserted events in the current transaction (`xmin = pg_current_xact_id()::xid`) after the operation start; unrelated/pre-existing/concurrent same-actor history is never annotated. JSON contains only changed allowlisted business fields. Numeric values are decimal strings. No private audit payloads, secrets or documents are exposed.

Address, contact, link, primary-marker, note and status changes no longer append an event to any property, including the shared-contact edits that previously fanned out to every property linked at that instant; they remain attributable in the private audit trail (`private.audit_events`) with actor, time and before/after values for as long as that trail's own 90-day retention window keeps them. A recorded asking-price change still records actor/time/before-after in the same transaction. Existing imported history is not invented or backdated. Consumers order/keyset-page on `(occurred_at,id)` within a property; the supporting index is property-scoped. Report/completion features remain issue #32's scope.

`public.property_price_history` is the issue-#36 Asking-price read over the same table: a select-only `security_invoker` view with one row per recorded price revision per series (`sale`, `rent`), exposing property, actor snapshot, authoritative time, the revision's retained explanation and exact whole-VND `before_value`/`after_value` text extracted with `->>`, so JSON serialization never rounds a large amount. `null` is an unknown gap and a recorded `'0'` stays zero; rows whose recorded price is unknown on both sides are excluded, so an untouched fact never appears as a price change. Each series keyset-pages on `(occurred_at,id)` through the matching partial index, and every read inherits live membership plus the archived-property RLS boundary. Achieved sale prices, contractual rent, dues and receipts are not in this view.

## Correction requests

Forward migration `20261011060659_correction_requests.sql` adds SELECT-only `correction_requests` and immutable `correction_amendments` with explicit grants/RLS. Any active employee submits an issue on a readable unarchived property; submission never changes inventory. Targets identify a property, address, shared contact linked to that property, or local link. Null address/link target reports a missing relationship/address. Categories: `incorrect`, `missing`, `other`. Explanation: 10–2000 characters. Replacement fields may be unknown (`{}`). Original observed allowlisted state, entity/parent revisions, requester and original proposal remain immutable.

- `submit_correction(p_property_id,p_target,p_target_id,p_category,p_explanation,p_changes,p_revision,p_property_revision) → uuid` captures authoritative observed state under revision checks.
- `amend_correction(p_request_id,p_request_revision,p_explanation,p_changes,p_revision,p_property_revision) → void` appends a separately attributed observation/proposal, preserving the original. The requester or authorized staff may amend an open request; staff reconciliation is explicit evidence, not automatic merging.
- `decide_correction(p_request_id,p_request_revision,p_action,p_reason,p_changes=null) → void`: `apply`/`reject` require staff/manager/admin; `withdraw` requires the requester. Apply/reject require a meaningful reason of 10–2000 characters, stored trimmed; a raw value over 2000 characters is refused rather than stored. Apply uses the latest original/amended observation and revisions, with the processor's optional replacement fields, then commits the actual maintenance and the `applied` outcome together. The applied proposal must differ from the live observed value it was proposed against, whether or not the history records the change; when the correction changes an asking price the retained outcome reason is attached to that price revision, and a price change that records nothing is refused. Issue-only application needs actual correction fields. No reviewer/requester confirmation follows. Legal/review/archive corrections are excluded; existing sold/rented/rental constraints still apply.

States: `open`, `applied`, `rejected`, `withdrawn`. Original submissions/amendments/terminal attribution remain retained; terminal reapplication and stale decisions fail. A shared maintenance gate then parent→request→target row locks serialize apply/reject/withdraw with one winner. Requesters read only their own requests/amendments; staff/manager/admin read the company queue subject to live property access. Shared property access does not grant sales another request's contents. Live deactivation and archived-property read boundaries also apply to requests/amendments/history. No mutation via direct Data API writes.

## Application boundary

The protected app shell hosts creation, immediate maintenance, correction submission/processing and property history in VI/EN. Language preference continues through `set_my_locale`; source text, phones and exact numeric strings are not translated or coerced. Staff contact selection distinguishes identity UUIDs and source phone spelling rather than deduplicating similar names/masks. Shared-contact saves and correction applications require an affected-property preview and explicit same-person confirmation in the UI, supplemented by database revision/access checks. The shared-contact editor is reachable by every active employee from a readable property and from the People → Contacts directory (issue #71), but an ordinary employee may save only a contact linked to a readable property; creating a contact and adding/replacing/unlinking a relationship stay staff/manager/admin controls, and the unlinked-identity editor is offered from the directory to staff/manager/admin only (issue #72). The directory lists each identity once with its readable per-property relationships and opens its recorded details, affected properties and same-person-confirmed correction in one expanding row; nothing is copied onto a property and no second owner store exists.

Same-origin, session-scoped APIs validate keys, revisions, target fields, enums and numeric/source types. Feature JSON POSTs use a bounded 256 KiB streamed body budget for multi-field UTF-8 input; existing authentication callers retain their 8 KiB budget. Forward migration `20261011180000_maintenance_review_followups.sql` raises the database maintenance size cap to that same 256 KiB budget so it cannot refuse a legitimate accepted change set. Origin checks and stream cancellation remain enforced. SQL errors become sanitized codes; `PT409` becomes HTTP 409 with retained drafts and a current-record reconciliation link, not automatic retries.

History is keyset-paged on timestamp/UUID. `GET /api/properties/[id]/price-history?series=sale|rent&before=&beforeId=` returns one keyset page (30) of a property's recorded price series with the same live-session and property-read boundary; `series` and both cursor parts are validated. `POST /api/properties/[id]/maintenance` accepts the optional `explanation` only for a property facts change that includes a price field and forwards it to the revision-checked RPC. Correction lists are bounded to 30 requests with one latest embedded amendment each; full immutable amendments are lazily ordinal-paged 20 at a time. Request/evidence reads remain subject to their own RLS and property access. Authenticated data is no-store; denial clears the existing protected surfaces rather than retaining successful previous data.
