# Spec #33 — Private property files

Source: https://github.com/Leonard-Data/SGN-Inventory/issues/33. This is the approved target contract; implementation and executed acceptance are recorded separately.

## Problem Statement

Employees need to attach certificates, land records, other documents and property photos to the company's shared property inventory, categorize them meaningfully and read them privately. They should not need a manager's document approval before a successfully uploaded file becomes available to authorized colleagues.

Network interruption, closing the browser or an ambiguous completion response must not lose the registered upload, create duplicate attachments or make incomplete files readable. Property cards need an intentionally selected photo of the property rather than whichever image happened to be uploaded first; a certificate scan must not accidentally become a card image.

The current package is an engineering and database foundation, not a working inventory application. It has registered file metadata, immutable private Storage paths, fixed document types and upload/review RPCs. Completion checks object registration exists, not actual byte count, hash or content type. Upload authority currently depends on property-edit authority. Employee-created categories, category correction, interruption recovery and explicit card-cover selection are not implemented. Spec #7 explicitly excludes new upload/download and legal-document processing surfaces; this is a separate specification and does not expand that issue.

## Solution

Provide a bilingual company-file journey integrated with property details and inventory cards:

- Any active employee may upload documents or photos to any unarchived property, independently of permission to edit property facts.
- Each file has one Document category, default Other. Active employees create and reuse company-wide categories. Its uploader or an authorized property editor may correct the category while the property is unarchived.
- Register before upload; validate completion automatically; recover the same registered upload after interruption, refresh, closing the browser or a subsequent login.
- Successfully validated files become privately readable by authorized property readers without a human document-review gate. Sharing a certificate does not verify its authenticity or legal ownership.
- Only an authorized property editor may select, replace or clear one Property cover photo. A completed Property photo is eligible; a document scan is not. Show a neutral placeholder when none is selected.
- Preserve existing employee access, archived-property boundaries, private signed reads and unrelated reservation, physical-visit and rental approval rules.

## User Stories

1. As an active employee, I want to attach a certificate or land record to an unarchived property, so that colleagues can use the company's supporting documents.
2. As an active employee, I want to upload to a property created by another employee, so that company-file contribution does not depend on property ownership in the application.
3. As a salesperson, I want file contribution not to grant property-edit permission, so that I can add evidence without changing facts outside my authority.

6. As a property reader, I want file availability not to imply verified legal ownership, so that I do not mistake an attachment for a legal decision.
7. As a property reader, I want certificates and other documents accessible only within authorized company inventory access, so that they are not published publicly.
8. As an uploader, I want each file registered against the intended property before bytes are sent, so that it has a stable attachment identity.
9. As an uploader, I want clear rejection of an unsafe filename, so that file paths cannot escape the registered attachment.
10. As an uploader, I want PDF, JPEG, PNG and WebP files supported, so that common documents and property photos can be shared.
11. As an uploader, I want unsupported file formats rejected clearly, so that I know what I must provide instead.
12. As an uploader, I want files over 20 MiB and empty files rejected, so that I do not attempt unsupported uploads.

14. As an uploader, I want expected byte count and hash checked against stored bytes, so that incomplete or changed content is not reported as successful.
15. As a property reader, I want incomplete or invalid uploads excluded from readable files, so that I cannot open an attachment that has not passed completion validation.
16. As an uploader, I want a clear per-file success or failure state, so that I can distinguish completed attachments from interrupted attempts.
17. As an uploader, I want my registered upload recoverable after a network interruption, so that a transient connection failure does not require creating another attachment.
18. As an uploader, I want recovery after refreshing the page, so that browser navigation does not lose the upload identity.
19. As an uploader, I want recovery after closing and reopening the browser, so that I can continue work later.
20. As an uploader, I want recovery after signing in again, so that upload progress is not tied to one browser session.
21. As an uploader, I want completion retried when the object already exists, so that an interrupted response does not cause a duplicate upload.
22. As an uploader, I want to reselect the same file when bytes still need uploading, so that recovery works without promising automatic access to local files after browser closure.
23. As an uploader, I want a different file rejected as a retry of the original registered upload, so that an ambiguous retry cannot silently replace its intended contents.
24. As an uploader, I want repeated completion attempts to converge on one attachment, so that uncertain responses do not create duplicates.
25. As an uploader, I want a fresh read of authoritative state after an ambiguous response, so that the interface does not falsely report failure or success.
26. As a property reader, I want completed objects immutable to ordinary clients, so that an existing file link cannot silently start serving different bytes.
27. As an uploader, I want replacement content registered as a new attachment with a new path, so that existing content and references remain intact.
28. As an active employee, I want to choose one Document category for a file, so that its classification is unambiguous.
29. As an uploader, I want Other used when no specific category is selected, so that classification does not block an otherwise valid attachment.
30. As an active employee, I want to create a category without admin approval, so that classifications can reflect the company's actual documents.
31. As an active employee, I want categories reusable across properties and employees, so that classification is company-wide rather than a private list.
32. As an uploader, I want to correct my own file's category on an unarchived property, so that I can fix a classification mistake without gaining property-edit rights.
33. As an authorized property editor, I want to correct an attached file's category, so that shared inventory remains organized even when the uploader is unavailable.
34. As an employee without file-category maintenance authority, I want another employee's classification protected from my changes, so that upload contribution does not confer unrestricted maintenance permission.
35. As a property reader, I want corrected categories reflected in fresh file lists, so that I do not continue using stale classifications.
36. As an uploader, I want to distinguish a Property photo from an image of a document, so that photographic property presentation is not confused with evidence format.
37. As an active employee, I want to upload multiple property photos as separate attachments, so that useful views can be retained without replacing existing images.
38. As an authorized property editor, I want to explicitly select one completed Property photo as the cover, so that the inventory card represents the property intentionally.
39. As an authorized property editor, I want to replace the selected cover with another eligible photo, so that the card can use a better view without deleting either attachment.
40. As an authorized property editor, I want to clear the cover selection, so that a misleading presentation can be removed without deleting the underlying photo.
41. As an inventory reader, I want a neutral placeholder when no cover is selected, so that the application does not invent a representative image.
42. As an inventory reader, I want certificate scans excluded from cover selection, so that legal documents do not accidentally become property-card images.
43. As an employee who can upload but cannot edit the property, I want cover changes denied, so that contributing a photo does not grant authority over the property's shared presentation.
44. As an authorized property editor, I want incomplete or invalid photos ineligible as covers, so that the card uses only validated attachments.
45. As an inventory reader, I want cover changes reflected in fresh inventory cards and property details, so that the selected representation is consistent.
46. As a property reader, I want to open or download a completed file through a short-lived private signed link, so that access does not require public Storage URLs.
47. As a property reader, I want private cover images subject to the same live property access, so that card rendering does not expose photos outside inventory permissions.

51. As an administrator, I want archived-property file access to retain the existing reviewer-only boundary, so that this feature does not broaden archival visibility.
52. As an employee, I want archived-property uploads, category corrections and cover changes denied, so that file contribution cannot bypass the archive boundary.

56. As an English-speaking employee, I want equivalent English labels, validation and states, so that the same feature is usable in English.
57. As an employee switching interface language, I want document bytes, filenames and custom category names left unchanged, so that interface preference does not rewrite company evidence.
58. As an employee, I want my saved interface language respected through the existing locale preference mechanism, so that file handling uses my established preference.
59. As an administrator, I want document contents and signed bearer links excluded from logs and shared public caches, so that observability and image rendering do not expose private files.
60. As an administrator, I want completion, category and cover rules enforced for direct API calls as well as UI actions, so that hidden buttons are not the security boundary.
61. As a reservation or rental user, I want existing ready-file evidence references preserved, so that file classification changes do not break established workflows.
62. As an administrator, I want previous file identities, contents and historical attribution preserved through the transition, so that removing document review does not erase evidence history.
63. As an employee reporting a physical visit or requesting a reservation, I want its independent review rules unchanged, so that removing document approval does not weaken unrelated company controls.

## Implementation Decisions

- **Architecture and modules:** retain one Next.js App Router/TypeScript application, one Supabase Postgres database and Vercel hosting. Build or modify the property-file registration/upload/completion/recovery, company Document category, private file-read and Property cover photo interfaces, integrating them with inventory cards, property details, employee access and localization. Keep rendering separate from feature-level data access; no unrestricted parallel CRUD interface.
- **Live authority:** validate the session server-side and require a linked Active employee on protected requests. Use request-scoped user-session Supabase clients with the publishable key; ordinary reads and writes remain subject to RLS. No raw-session authorization, editable-metadata role source or secret/service-role fallback for ordinary app requests. Preserve established authenticated denial and sensitive-state clearing behavior.
- **Upload authority:** all Active employees may register and upload to any unarchived property, including another employee's property. Change the current property-edit-dependent file policies rather than treating hidden UI controls as permission. File contribution grants no property, contact, legal-status, rental or reservation authority. Derive uploader identity from the live session.
- **Classification model:** each Property file has one company-wide Document category. Add employee-created category storage and explicit grants/RLS with a required Other default, reuse across employees/properties and validated nonblank labels. Treat the built-in Other label as localized interface text while preserving employee-created names verbatim. Prevent duplicate normalized names and reconcile concurrent attempts to create the same category by returning/reusing the existing category. Normalize surrounding whitespace and case for duplicate detection without removing Vietnamese accents or translating names. Do not add rename, merge or delete operations.
- **Classification mutation:** permit category changes only by the original uploader or an authorized property editor on an unarchived property. Validate category identity and live permissions in the database; preserve file identity, bytes, original filename, uploader and existing evidence references. Category assignment does not alter legal status or make a pending upload ready.
- **Photos and cover:** keep attachment purpose distinct from MIME and flexible category names: an image of a document is not a Property photo just because it is JPEG/PNG/WebP. Record Property photo versus document intent during registration. The property has at most one explicit cover reference to a completed, content-validated Property photo on that same property. Only an authorized property editor may set, replace or clear it while unarchived. No first-image fallback, automatic assignment on upload or category-name-based cover eligibility. Clearing/replacing the cover does not delete attachments. Refresh affected card/detail data after successful changes.
- **Immutable upload identity:** register metadata before Storage insertion with a stable file UUID, property binding, safe filename, expected MIME/byte count/SHA-256 and an immutable property/file/filename path. Preserve the private bucket and disallow ordinary client upsert, object overwrite and deletion. Replacement content receives a new UUID/path; no global content deduplication or automatic replacement is introduced.
- **Allowed content and technical readiness:** retain positive byte size and PDF/JPEG/PNG/WebP support, with the per-file cap taken from that validated content type — at most 20 MiB for a document and at most 5 MiB for an image — and at most 5 documents and 10 images per property (the cover photo counted among the images). Check actual stored bytes for matching expected count/hash and supported content type; do not trust an extension, client MIME label or object-registration row alone. Technical validation is not human review, proof of authenticity or malware scanning. Incomplete/invalid objects remain unavailable for private reads, cover selection and ready-file evidence use.
- **Completion trust boundary:** preserve the public completion interface only if it enforces the strengthened ready-state contract. Close every direct metadata/Storage/RPC path that could mark unvalidated content ready. A client-supplied hash, success flag or validator identity is not evidence that validation occurred. Establish verifiable technical completion using user-scoped operations without a privileged ordinary-request bypass; pending-byte inspection must be narrowly limited to the registered uploader with live property access, not company-wide pending-object reads. Recheck current access and authoritative object identity at finalization. Mutations are input-validated and guarded against unauthorized origin/CSRF use.
- **Interruption recovery:** recover registered uploads belonging to the signed-in uploader after refresh, browser closure and subsequent login. If complete immutable bytes already exist, retry validation/completion; if no complete object exists, let the employee reselect the matching original file and reupload with the same registered identity. Never interpret a network error as proof that bytes are absent; refetch authoritative state after ambiguous outcomes. Hash/count checks reject different content submitted as a retry. Repeated/concurrent finalization converges on the same attachment. Do not promise browser access to local files after closure or byte-range transfer resumption.
- **No document-review workflow:** validated readiness makes files available without accepted/issue_flagged transitions or reviewer approval. Retire the document-review application/RPC mutation path; migrate callers and prevent a legacy path from changing current file state. Preserve existing/imported files, identities, original content, evidence references and historical attribution rather than destructively rewriting or discarding past review records. Do not alter property legal status automatically or remove unrelated reservation, visit, address-verification or rental review safeguards.
- **Read and archive boundaries:** completed files follow property-read access: active internal property readers, with archived properties/files limited to manager/admin under the existing reviewer boundary. Upload, recategorization and cover mutations require an unarchived property. Metadata lists and image delivery must not bypass the parent property's boundary. Check live membership for recovery, completion, category creation/assignment, cover changes and signed-read requests; deactivate/unlink denial holds with previously issued JWTs.
- **Private rendering:** authorize each new signed file/image read and use short-lived signed URLs, recommended 60 seconds. Links are bearer credentials until expiry, not immediately revocable through employee deactivation. Handle expiry by obtaining another authorized link only while access remains valid. Do not persist URLs in metadata, print them in logs or use shared public caches/image-optimization paths that expose authenticated images. Clear private display state on the established access-denial/session transitions; previously delivered information cannot be recalled.
- **Localization:** provide equivalent VI/EN file lists, category selection/creation, upload/recovery, errors, progress/completion, cover controls, placeholders and private-read states. Vietnamese is the default and preference is persisted through the existing locale interface. Preserve document bytes, original filenames, custom category names, Vietnamese source text and existing property/address/contact facts when switching language.
- **Schema cutover and delivery:** add new migrations rather than rewriting deployed SQL. Give all new exposed tables explicit grants and RLS in the same migration; anonymous inventory access remains forbidden. Public RPC wrappers remain invoker functions; privileged internals stay private with fixed search paths, explicit EXECUTE revocation and live-role checks. Migrate fixed document types into category assignments without dropping unmatched legacy classifications, preserving existing photo/document meaning and leaving cover selection explicit. Update affected callers, generated schema types, fixtures, invariant tests and approved contracts together. Verify current supported package/SSR APIs and retain pinned tooling before implementation.

## Testing Decisions

- **User-confirmed primary seam:** exercise the authenticated browser file journey against real isolated Supabase Auth, Data API/RLS and Storage. The user approved this seam with the six-ticket breakdown. This is the highest consumer-visible seam and covers the actual registration, upload, recovery, categories, covers, private reads and VI/EN surfaces. Do not introduce mocked data-access adapters or expose internal helpers solely for tests.
- **Supplementary existing seams:** reuse the embedded PostgreSQL integration harness and structural database checks for deterministic invariants, plus authenticated direct Data API/RPC/Storage attempts for bypass resistance. Use genuinely separate connections/sessions when demonstrating concurrency; parallel calls on one embedded connection are not proof. These support, not replace, the browser-primary seam.
- **Good tests:** test observable behavior, access boundaries, exact state transitions, preserved content/identity, rollback, errors and concurrent outcomes. Use isolated sanitized fixtures, distinct authorized/unauthorized actors and unrelated-property controls. Avoid assertions about source text, component wiring, private calls, forwarding echoes, incidental defaults or bare non-throwing outcomes.
- **Prior art:** the current embedded integration harness uses employee/session fixtures and public database interfaces for registration, completion without bytes, direct-ready update denial, unregistered upload denial, pending invisibility, ready reads, object overwrite denial and inactive-employee denial. Reuse that approach for new invariants. Its Storage/Auth shims check database behavior only; object-row insertion does not prove real uploaded bytes, HTTP Storage behavior or signed-link acceptance.
- **Upload permission and isolation:** prove a salesperson can upload to another employee's unarchived property but cannot edit that property's facts, change its cover or recategorize another uploader's file without edit authority. Prove inactive/unlinked/anonymous and archived-property mutation denial through both browser and direct API interfaces; denied operations leave authoritative state unchanged.
- **Actual content and completion:** upload real sanitized valid PDFs and supported property/document images. Test absent bytes, truncated content, mismatched byte count/hash, spoofed MIME/extension, empty/oversize inputs and unsupported formats. Inspect authoritative readiness and read/cover denial after each failure. Direct calls must not bypass validation by forging expected metadata or invoking the old completion path.
- **Recovery and convergence:** interrupt before object creation, after bytes are stored but before completion, and after completion but before its response is observed. Exercise refresh, tab/browser closure and subsequent login, reselection of matching versus different local content, and repeated/concurrent completion. Assert the same file identity/path, exact expected bytes, one attachment and correct final readiness rather than just a successful UI message.
- **Categories:** prove one category per file, Other when none is selected, employee-created company-wide reuse, normalized duplicate/concurrent creation behavior, and preservation of Vietnamese accents/custom names. Exercise uploader versus property-editor category correction and denial for unrelated contributors. Verify category changes do not mutate bytes, readiness, legal status or evidence references.
- **Photos and covers:** use a Property photo and an image of a certificate as distinct fixtures. Prove explicit eligible selection, same-property binding, no automatic cover from either upload, placeholder without selection, denial of pending/invalid/document cover candidates, authorized replace/clear and preservation of all attachments. Observe fresh card/detail rendering without public image leakage.
- **Private reads and live membership:** prove allowed ready-file reads, denied pending/invalid/unauthorized reads, archived reviewer boundaries, signed-link expiry and authorized renewal for documents and covers. After deactivation with an existing JWT, new signed links and mutations fail and protected-request/refocus checks clear private UI state. Separately demonstrate that an already-issued bearer link may remain usable until expiry; do not assert instant recall.
- **Regression, history and cutover:** retain file identities/content/uploader attribution and prior historical records, preserve ready-file references used by reservations and rentals, remove current document-review gating and demonstrate no legal-status side effects. Keep independent reservation/visit/rental decisions intact. Prove old direct mutation paths cannot circumvent the new permission, validation, category or cover rules.
- **Browser/localization and gates:** run the actual VI/EN upload/category/recovery/cover/read journey with actionable errors and unchanged filenames, category names and document content. Verify private response/cache behavior and safe diagnostics. Run the existing schema test command for schema/workflow implementation, then real staging browser/API/RLS/Storage and multi-session acceptance before claiming delivery. Record sanitized actual results only; provisioning and deployment need separate authorization.

## Out of Scope

- Human document acceptance, issue-flagging/review queues, independent document approval, legal authenticity verification, proof of ownership, automatic property legal-status changes, OCR, document translation and malware scanning.
- Multiple tags per file; category renaming, merging or deletion; global file deduplication; automatic cover selection; image editing or a new image-processing service.
- HEIC, video, Office documents or other additional formats; files above 20 MiB; byte-by-byte resumable transfer; automatic recovery of access to local files after browser closure.
- Ordinary client object overwrite/deletion, removal/replacement of other employees' files, destructive cleanup or automatic orphan sweeps. Any Storage cleanup remains separately authorized audited administrative maintenance.
- Expanded property/contact edit authority; changes to established archived-property boundaries; legal, reservation, physical-visit, address-verification or rental approval rules outside this file integration.
- Public document/image access, permanent shared links, external notifications, maps, AI matching, multi-tenancy, commission/payment calculations, payment gateways or general accounting.
- Employee invitation/linkage/activation administration, a broader authentication redesign, production customer-data import, Supabase provisioning or application deployment under this specification-publication request.
- Rewriting or expanding Spec #7; this private-files journey is independently specified.
