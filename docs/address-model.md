# Vietnamese legacy and current address model

## Evidence baseline

Decision 19/2025/QĐ-TTg provides the official province and commune code lists effective from 1 July 2025. The two-tier administrative model operates from that date. District labels are therefore retained for historical addresses and search, while current structured entry uses province/city and commune/ward. The HCMC reorganization in Resolution 1685/NQ-UBTVQH15 includes partial ward transfers. A ward-name substitution alone cannot resolve every property. See official links in `sources.md`.

This is an application data model derived from those sources. It does not establish legal title or alter a document's original address. Catalog ingestion must check for subsequent official changes rather than treating the 2025 list as permanently current. The seeded reference catalog below is pinned to a later upstream revision, so check for changes after that revision before ingesting any newer release.

## Entry and display rules

| Situation | Data captured | UI behavior |
| --- | --- | --- |
| New property with current address | Current province and ward selections, house number, street, entered text; save provenance | Default form; dependent ward list; hide district; show candidate until reviewed |
| New property known only by old address | Legacy province/city, district and ward/commune picked from the pre-2025 official list, district text, street, house number, original text | Explicit “Địa chỉ cũ”; save successfully, then the save reports what the official crosswalk says about that ward: one whole or rename target is offered as one explicit action that records the current address as an unverified candidate beside the preserved legacy row, several targets state the count and that the new ward needs verification, and no row states that no mapping is available. Nothing is written automatically, and the create confirmation and the Edit facts dialog hold that report open instead of closing ([maintenance contract](maintenance-contract.md)) |
| Imported legacy row | Preserve original full address and raw structured labels | Show “Địa chỉ cũ”; current address may be absent |
| Legacy ward corrected after a candidate was recorded | Legacy successor row records the corrected ward | The save reports what the ward the row now records maps to — its single target and one action, several targets, or none — instead of the state recorded for the ward it no longer names; that new ward's target records once and a repeat is refused |
| One whole verified unit transition | Build a current candidate from official lineage and unchanged local address | Reviewer validates property/street evidence before marking verified |
| Partial unit transition | No address row is written; the crosswalk rows for the old ward are counted | “Cần xác minh phường mới” with that count, so the new ward is stated as needing verification rather than guessed; a reviewer resolves it with boundary/location/document/manual evidence |
| Old/new address on a certificate | Store address exactly as printed as evidence; retain uploaded document | Display beside current inventory address; never rewrite file contents |
| New official change after initial release | Insert new dated unit versions and transition records | Keep earlier addresses; update primary current address only after reviewed mapping |

Recorded address text and selected official unit names are searched through `property_addresses.search_text`, so a dropdown-only address remains searchable even without a source label. The property record reads a legacy address as it was recorded: the source text unchanged, the official province → district → ward names of the units it chose beside it, and one line of crosswalk state for its ward — the single current ward the official row names, the count that needs verification, or that no row exists — in the same words the save surface reports. The browser's local address index folds each variant on its own recorded text, address parts and chosen official unit names, so a ward chosen from a list is matched by its official name, and between the two variants of one property the one whose own recorded locality answers more of the query in a single field decides the recorded format shown - so a search for an old district still finds the property under its legacy label after a current candidate is recorded, while a search for the new ward finds it under its current one. Where the old district's words are also the new ward's name, the label is decided the same way: the variant that states the searched locality in one of its own locality fields answers it, a recorded column before an official unit name that only contains those words, and a query naming neither tier answers with the legacy record rather than with whichever address is listed first. Address entry uses the same official province/city and commune/ward selectors for current and legacy formats, and a legacy address adds the district level between them: choosing `legacy` offers three dependent pickers reading the pre-2025 three-tier catalog (province → that province's districts → that district's wards), while `current` keeps the two-level province → commune entry and refuses a district. A unit an address recorded before this entry existed keeps its stored identifier and is offered under its own official name even when that identifier belongs to the other catalog generation; entry never rewrites it. Recorded source labels remain provenance rather than separate editable replacement fields, and a district pick rewrites the free-text `district_text` whenever that field holds nothing or the official name of the district the address records, so a re-pick — in this form or a later one — replaces the label the picker wrote and a province change clears it, while a person's own wording is never overwritten; the field is editable either way. The edit form keeps the recorded format and never offers a switch between them; whether an edit should be able to change an address's format is held for the captain. Picker options show the official name alone, adding validity dates only when duplicate names in one list need disambiguation. The first release displays a verified current address as primary when available; otherwise the old address remains the usable address. A current candidate can be displayed with a warning, but must not appear as verified in area analytics.

## Model example (illustrative)

`properties.id` identifies the building or parcel; it does not change when a ward changes. A property may have:

- A primary legacy address with city/district/ward labels and the untouched source full text.
- A primary current address with province/commune version IDs and no district.
- Additional nonprimary/alternate addresses for historical documents or aliases.

Version records hold official text codes, names, parents, validity dates and source URLs. Dates use `[valid_from, valid_to)`; NULL `valid_to` means no known end date. Crosswalk rows link old/new version IDs and state whether the change covers the whole unit, part of it, or a rename. These are a candidate-generation aid, not property-level proof.

## Verification workflow

1. Load official catalogs into an unpublished review batch; validate code/name/level, parent relationships, duplicate/overlapping validity and source provenance.
2. Match legacy labels using province **and** district **and** ward. Names such as “Phường 1” are not globally unique.
3. Create crosswalk candidates from official transition evidence. Never infer a missing `BDS-` property alias from an address mapping.
4. Resolve a split using property-level evidence. Manual decisions record reviewer, time, source and method.
5. Save the current address with verified unit IDs and the date on which those units apply. The database validates levels, parents, date validity and absence of district.
6. Retain the legacy address. For a later change, retain the previous current row as nonprimary before adding a replacement within one transaction.

Complete verified HCMC data first because all nonblank city labels in the property sheet are HCMC. Do not assume every physical location is correct merely because that column says HCMC.

### Seeded reference catalog

Migration `20261014075435_vietnamese_admin_units_reference.sql` seeds the national two-tier catalog into `admin_unit_versions` from the pinned [vietnamese-provinces-database](https://github.com/thanglequoc/vietnamese-provinces-database) PostgreSQL releases: 34 province/city units and 3321 ward/commune/island-special-region units across 37 province/city version rows and 3569 ward/commune version rows, each carrying the official numeric code, the province → commune parent link and one half-open `[valid_from, valid_to)` window per official name. The 2025-07-01 baseline window uses the pre-2026 official names from the [v3.0.2](https://github.com/thanglequoc/vietnamese-provinces-database/tree/v3.0.2) snapshot (data-file md5 `d2a3372d23480d75d2d32710707df98b`; later upstream diacritic corrections are kept); the dated windows use the [v5.2.0](https://github.com/thanglequoc/vietnamese-provinces-database/tree/v5.2.0) names (tag commit `62b1abdfe39625289c37a58ef6678e9db3d37f84`) for `Tỉnh Đồng Nai → Thành phố Đồng Nai` and ten Đồng Nai `Xã → Phường` promotions on 2026-04-30 (Nghị quyết 30/2026/QH16 and 237/NQ-UBTVQH16), `Tỉnh Quảng Ninh → Thành phố Quảng Ninh` on 2026-09-01 (Nghị quyết 36/2026/QH16), and `Tỉnh Bắc Ninh → Thành phố Bắc Ninh` with twelve Bắc Ninh `Xã → Phường` promotions on 2026-09-20 (Nghị quyết 39/2026/QH16 and 388/NQ-UBTVQH16). Codes, names and hierarchy are upstream verbatim; `name_vi` is the upstream `full_name`, with the one upstream record whose `full_name` had a lowercased type prefix (`06325`) taking the upstream canonical type label. A renamed province also carries its commune rows forward into the new window, so a verification dated inside a renamed period reports the name in force then and both windows keep a complete picker hierarchy.

The catalog is a reference list, not a property-level verification. Selecting a province and commune from it does not establish a property's current address; a manager/admin still records evidence before `mapping_status = 'verified'`. The seed is idempotent and never rewrites a recorded address string.

Not seeded by this package: any blanket mapping, any HCMC parcel-level resolution of a `partial` transition, and any automatic property mapping. The official old→new crosswalk **is** seeded by `20261021080934_admin_unit_crosswalks_official_ingest.sql` (10,622 rows: 63 province-level, 5 district-level, 10,554 ward-level), and a migration-seeded row counts as reviewed whole-mapping evidence through its `source_attested` marker; the crosswalk is migration-only, since `20261021080935_admin_unit_crosswalks_write_boundary.sql` revokes client writes. A district-level catalog is seeded too, but only for the pre-2025 window: migration `20261021060602_legacy_admin_units_reference.sql` adds the 63 legacy provinces, 696 legacy districts and 10,051 legacy wards of the pinned VietnamProvinces snapshot on the closed `[2025-01-04, 2025-07-01)` window, so a legacy ward has a real district parent, and the address form's `legacy` format reads those rows through three dependent pickers (`src/features/property-maintenance/forms.tsx`). Reporting reads none of them: the property record states a legacy address's own hierarchy and its ward's crosswalk state, and maps nothing.

## Analytics and search

Current-area dashboards count properties with a **verified** current commune and place the remainder in “Chưa xác minh địa chỉ mới”. Old district is available as a historical reporting grouping. Do not present old-district geography as a current administrative hierarchy. Searches may match any address; result labels must indicate legacy/candidate/verified to explain the match.
