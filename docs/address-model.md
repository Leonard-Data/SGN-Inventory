# Vietnamese legacy and current address model

## Evidence baseline

Decision 19/2025/QĐ-TTg provides the official province and commune code lists effective from 1 July 2025. The two-tier administrative model operates from that date. District labels are therefore retained for historical addresses and search, while current structured entry uses province/city and commune/ward. The HCMC reorganization in Resolution 1685/NQ-UBTVQH15 includes partial ward transfers. A ward-name substitution alone cannot resolve every property. See official links in `sources.md`.

This is an application data model derived from those sources. It does not establish legal title or alter a document's original address. Catalog ingestion must check for subsequent official changes rather than treating the 2025 list as permanently current. The seeded reference catalog below is pinned to a later upstream revision, so check for changes after that revision before ingesting any newer release.

## Entry and display rules

| Situation | Data captured | UI behavior |
| --- | --- | --- |
| New property with current address | The stated province/city and the chosen ward, house number, street, from which the server composes the address text; save provenance | Chosen as `current` on the format control, which starts a new address on `legacy`; the province is stated rather than chosen, so only the ward is picked from a list that narrows inside it; hide district; show candidate until reviewed |
| New property known only by old address | The stated province/city plus the legacy district and ward/commune picked from the pre-2025 official list, district text, street, house number, from which the server composes the address text | Explicit “Địa chỉ cũ”; save successfully, then the save reports what the official crosswalk says about that ward: one whole or rename target is offered as one explicit action that records the current address as an unverified candidate beside the preserved legacy row, a ward whose recorded rows are anything but exactly one whole or rename row — a single `partial` successor included — states how many recorded crosswalk rows need verification, and no row states that no mapping is available. Nothing is written automatically, and the create confirmation and the Edit facts dialog hold that report open instead of closing ([maintenance contract](maintenance-contract.md)) |
| Imported legacy row | Preserve original full address and raw structured labels | Show “Địa chỉ cũ”; current address may be absent |
| Legacy ward corrected after a candidate was recorded | Legacy successor row records the corrected ward | The save reports what the ward the row now records maps to — its single whole or rename target and one action, how many recorded crosswalk rows need verification, or none — instead of the state recorded for the ward it no longer names; that new ward's target records once and a repeat is refused |
| One whole verified unit transition | Build a current candidate from official lineage and unchanged local address | Reviewer validates property/street evidence before marking verified |
| Partial unit transition | No address row is written; the crosswalk rows for the old ward are counted | “Cần xác minh phường mới” with that count, so the new ward is stated as needing verification rather than guessed; a reviewer resolves it with boundary/location/document/manual evidence |
| Old/new address on a certificate | Store address exactly as printed as evidence; retain uploaded document | Display beside current inventory address; never rewrite file contents |
| New official change after initial release | Insert new dated unit versions and transition records | Keep earlier addresses; update primary current address only after reviewed mapping |

The recorded address text is the server's composition of the parts, never a field a person fills in: it reads *house number, street, commune, district, province* for a legacy address and the same line without the district for a current one, a missing part is skipped, and the official name of the unit an address records wins over a recorded source label, which names only a level the address records no unit for (`private.composed_address_text`, issue #277). Both creation and editing compose it, while a mapping change moves only the units and leaves the row's recorded text exactly as it is, so the form, the API and every other client can only state parts; a save that carries a text of its own is refused - a correction proposal, amendment or decision included - the import preserves the workbook's own legacy address text as source evidence, and the imported rows keep the wording they already hold; the import's current-address builder follows the same `", "` rule over house number, street, commune and province. The stored text is the single source of truth for display: the inventory table's address column and the quick view opened from a row state it as recorded, never a recomposition from the parts, so an imported row reads as the wording it was imported with and a newly composed address reads as composed (issue #278).

Recorded address text and selected official unit names are searched through `property_addresses.search_text`, so a dropdown-only address remains searchable even without a source label. The property record reads a legacy address as it was recorded: the source text unchanged, the official province → district → ward names of the units it chose beside it, and one line of crosswalk state for its ward — the single current ward the official row names, the count that needs verification, or that no row exists — in the same words the save surface reports. The browser's local address index folds each variant on its own recorded text, address parts and chosen official unit names, so a ward chosen from a list is matched by its official name, and between the two variants of one property the one whose own recorded locality answers more of the query in a single field decides the recorded address shown - so a search for an old district still finds the property under its legacy address after a current candidate is recorded, while a search for the new ward finds it under its current one. Where the old district's words are also the new ward's name, the address shown is decided the same way: the variant that states the searched locality in one of its own locality fields answers it, a recorded column before an official unit name that only contains those words, and a query naming neither tier answers with the legacy record rather than with whichever address is listed first. Address entry offers those two formats and no other: the format control starts a new address on `legacy` and opens a recorded one on the format it holds, and a row an import recorded as `alternate` reads back as what it holds without being offered. A created address must name a house number, a street or a commune picked from the catalog, because the text is composed from those parts and the province the app states is not an address; an ordinary edit is unaffected and may leave the recorded parts exactly as they are. The business records addresses in one province, so both formats state Thành phố Hồ Chí Minh (`cc2ace6d-f3e8-424c-9105-a560983abae0`, the one constant `FIXED_PROVINCE` in `src/features/property-maintenance/units.ts`) instead of offering a province selector, and only the levels beneath it are picked: a legacy address adds the district between them, offering the pre-2025 three-tier catalog's districts of that province → that district's wards, while `current` lists that province's communes and refuses a district. An address records the stated province's row for its own catalog generation: `private.guard_address()` requires a district, and a commune, to be parented by the province and district the address records, so a legacy address stores that province's pre-2025 row (the row its district hangs off) and a current address the current row. A record that already stores a province keeps its recorded `province_unit_id` on every save rather than being rewritten to the stated one, and a legacy address keeps its recorded source province and district text unchanged. A unit an address recorded before this entry existed keeps its stored identifier and is offered under its own official name even when that identifier belongs to the other catalog generation; entry never rewrites it. Recorded source labels remain provenance rather than separate editable replacement fields, and a district pick writes the chosen district's official name into the free-text `district_text`: a field already holding that name is left alone, while any other value — an imported shorthand included — is replaced, so a re-pick repairs the label, and a format change clears it. The address forms never offer the district text for typing, and a correction names the district unit rather than that text, but wherever a form offers the legacy district picker the label it writes rides along with it: a recorded value travels with the form on every other save rather than being blanked, and the recorded text reads back beside the district picker. An ordinary edit keeps an address in the format it was recorded in and never changes that field. Switching an existing address between the two formats is the one deliberate, labelled action: it records the other format's row from the official crosswalk as an unverified candidate, composed from the source parts and the target units, beside the preserved address, which stays present and unmodified, and it is offered only on a `legacy` or `current` row that no later row of the same format replaced ([maintenance contract](maintenance-contract.md)). Picker options show the official name alone, adding validity dates only when duplicate names in one list need disambiguation. The first release displays a verified current address as primary when available; otherwise the old address remains the usable address. A current candidate can be displayed with a warning, but must not appear as verified in area analytics.

## Model example (illustrative)

`properties.id` identifies the building or parcel; it does not change when a ward changes. A property may have:

- A primary legacy address with city/district/ward labels and the untouched source full text.
- A primary current address with province/commune version IDs and no district.
- Additional nonprimary/alternate addresses for historical documents or aliases.

Version records hold official text codes, names, parents, validity dates and source URLs. Dates use `[valid_from, valid_to)`; NULL `valid_to` means no known end date. Crosswalk rows link old/new version IDs and state whether the change covers the whole unit, part of it, or a rename. These are a candidate-generation aid, not property-level proof.

## Verification workflow

1. Load official catalogs into an unpublished review batch; validate code/name/level, parent relationships, duplicate/overlapping validity and source provenance.
2. Match legacy labels using province **and** district **and** ward. Names such as “Phường 1” are not globally unique.
3. Create crosswalk candidates from official transition evidence. Never infer a missing `BDS-` property alias from an address mapping.
4. Resolve a split using property-level evidence. Manual decisions record reviewer, time, source and method.
5. Save the current address with verified unit IDs and the date on which those units apply. The database validates levels, parents, date validity and absence of district.
6. Retain the legacy address. For a later change, retain the previous current row as nonprimary before adding a replacement within one transaction.

Complete verified HCMC data first because all nonblank city labels in the property sheet are HCMC. Do not assume every physical location is correct merely because that column says HCMC.

### Seeded reference catalog

Migration `20261014075435_vietnamese_admin_units_reference.sql` seeds the national two-tier catalog into `admin_unit_versions` from the pinned [vietnamese-provinces-database](https://github.com/thanglequoc/vietnamese-provinces-database) PostgreSQL releases: 34 province/city units and 3321 ward/commune/island-special-region units across 37 province/city version rows and 3569 ward/commune version rows, each carrying the official numeric code, the province → commune parent link and one half-open `[valid_from, valid_to)` window per official name. The 2025-07-01 baseline window uses the pre-2026 official names from the [v3.0.2](https://github.com/thanglequoc/vietnamese-provinces-database/tree/v3.0.2) snapshot (data-file md5 `d2a3372d23480d75d2d32710707df98b`; later upstream diacritic corrections are kept); the dated windows use the [v5.2.0](https://github.com/thanglequoc/vietnamese-provinces-database/tree/v5.2.0) names (tag commit `62b1abdfe39625289c37a58ef6678e9db3d37f84`) for `Tỉnh Đồng Nai → Thành phố Đồng Nai` and ten Đồng Nai `Xã → Phường` promotions on 2026-04-30 (Nghị quyết 30/2026/QH16 and 237/NQ-UBTVQH16), `Tỉnh Quảng Ninh → Thành phố Quảng Ninh` on 2026-09-01 (Nghị quyết 36/2026/QH16), and `Tỉnh Bắc Ninh → Thành phố Bắc Ninh` with twelve Bắc Ninh `Xã → Phường` promotions on 2026-09-20 (Nghị quyết 39/2026/QH16 and 388/NQ-UBTVQH16). Codes, names and hierarchy are upstream verbatim; `name_vi` is the upstream `full_name`, with the one upstream record whose `full_name` had a lowercased type prefix (`06325`) taking the upstream canonical type label. A renamed province also carries its commune rows forward into the new window, so a verification dated inside a renamed period reports the name in force then and both windows keep a complete picker hierarchy.

The catalog is a reference list, not a property-level verification. Selecting a province and commune from it does not establish a property's current address; a manager/admin still records evidence before `mapping_status = 'verified'`. The seed is idempotent and never rewrites a recorded address string.

A second seed covers the pre-2025 three-tier generation, and it comes from the other vendor: migration `20261021060602_legacy_admin_units_reference.sql` adds the 63 legacy provinces, 696 legacy districts and 10,051 legacy wards of the pinned [sunshine-tech/VietnamProvinces](https://github.com/sunshine-tech/VietnamProvinces) snapshot (tag `v2026.9.0`, tag commit `4cc4038d0e89bd8affbda864119c1ab1e0360523`, data file `dev/seed-data/Pre-2025-07/Xa_2025-01-04.csv`, sha256 `026361a37fd47ad469ec6d5cc6dbcf2f0ae8a5d4219d10482fbbc8689864a2a4`) into the same table, on the half-open `[2025-01-04, 2025-07-01)` window and with every row of that seed citing that file, so a legacy ward has a real district parent and the address form's `legacy` format reads those rows beneath the stated province through two dependent pickers, district then ward (`src/features/property-maintenance/forms.tsx`). `20261023040847_captain_requested_legacy_communes.sql` adds thirteen further communes the captain requested on 2026-10-23 to that same window under local non-numeric codes such as `Q10-03`, so the generation holds 10,064 wards; those rows are not snapshot data — their `source_url` marks them as captain-requested entries rather than official units — and a requested commune that already exists as an official row is not duplicated. The two vendors are kept apart by window and by `source_url`, which the two vendor seeds never share: the thanglequoc release the current catalog comes from is two-tier only — its schema has no district table — so districts and their wards can only come from the pinned three-tier snapshot, whose declared GPL-3.0-or-later licence with no LICENSE file is an open legal item rather than a settled one; only factual rows (official codes, names, parent links, dates) are vendored from either source, with no upstream code or transform. The window is half-open — 2025-01-04 is a legacy day and 2025-07-01 is not — and opens on the snapshot date, 2025-01-04, not on the date these units were created: an earlier `valid_from` would claim code assignments the source does not carry. A legacy address older than 2025-01-04 may therefore name a ward this catalog cannot offer; it saves as its recorded text with no unit ids and stays `unresolved`, exactly like any other legacy address no catalog unit was chosen for, and nothing rewrites it to fit a list.

The official old→new crosswalk is seeded in full by `20261021080934_admin_unit_crosswalks_official_ingest.sql`: 10,622 rows — 63 province-level, 5 district-level and 10,554 ward-level — each effective 2025-07-01, with the relation derived once per legacy unit by one stated rule (two or more successors or a stated partial absorption is `partial`, only the source's own rename notes are `rename`, everything else is `whole`). Coverage is 10,023 of the 10,051 legacy wards (9,578 `whole`, 441 `partial`, 4 `rename`); the remaining **28** wards carry no row at all, and a legacy save naming one states that no crosswalk is available for the saved ward instead of guessing, while a ward whose recorded rows are anything but exactly one whole or rename row — a single `partial` transfer included — states how many recorded crosswalk rows need verification. A seeded row has no employee to put in `verified_by`, so the same migration adds `source_attested` and the whole-mapping guard accepts `verified_by is not null or source_attested`, with every other evidence demand unchanged and a `partial` transition still never satisfying it: a crosswalk row is candidate evidence, never verification, and nothing promotes one on its own. `20261021080935_admin_unit_crosswalks_write_boundary.sql` drops the `admin_insert`/`admin_update` policies and revokes `insert, update` from `authenticated`, so the table is migration-only from now on — a missing or corrected row arrives as a new migration with its own source, never as an app edit.

Not seeded by this package: any property-level mapping decided in advance or applied automatically, and any HCMC parcel-level resolution of a `partial` transition. Reporting reads none of these rows: the property record states a legacy address's own hierarchy and its ward's crosswalk state, and maps nothing. No backfill is needed for the **18,801** imported properties: each already holds exactly the state this feature produces — the untouched legacy address as `unresolved` and, where the import resolved a bound, one `candidate` current address ([testing](testing.md)) — so entry, the save report and the conversion action read them as they are, and nothing is re-imported, re-mapped or re-verified.

## Analytics and search

Current-area dashboards count properties with a **verified** current commune and place the remainder in “Chưa xác minh địa chỉ mới”. Only a `verified` current address supplies a current province or commune label; a `candidate` supplies neither, so a crosswalk-derived row never reaches a verified area total (proved in `scripts/province-activity-contract.mjs`). Old district is carried as a separate historical reporting grouping from the recorded legacy `district_text`, so legacy geography never counts as a current area. Do not present old-district geography as a current administrative hierarchy. A search matches one recorded format at a time: the legacy address by default, the current address when the filter panel selects it, or either recorded format once the format filter is cleared (issue #243). A property recording no address in the selected format does not match rather than being given one. Result labels must indicate legacy/candidate/verified to explain the match.
