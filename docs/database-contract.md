# Database contract for the Next.js application and coding agents

Contract version: `0.2.0`; SQL schema authority: `supabase/migrations/`. Single company, invite-only employees, public Data API schema + unexposed private internals.

## Mandatory localization and rentals

Vietnamese (`vi`, default) and English (`en`) are both required in the application. Keep Vietnamese regional data conventions in either language; persist `employees.preferred_locale` through `set_my_locale`. UI language and signed rental document language are separate.

Rental lifecycle, monthly occupancy/dues and manual payment receipt/refund tracking are in scope. Use the normative [rental and localization contract](rental-localization-contract.md) for schemas, RPC parameters, status labels, authorization and acceptance rules. This adds rent tracking, without commission payouts or a payment gateway.

## Client and authorization contract

Use the signed-in user's request-scoped Supabase client with the publishable key. DB helpers find an **active** employee whose `auth_user_id = auth.uid()`. Application roles are stored in `employees.role`, not `user_metadata`. A signed-in Auth user without an active employee row has no inventory access.

Expose only `public` in the Data API. `private` must remain unexposed even though authenticated DB roles have USAGE and narrowly scoped helper EXECUTE permissions. Do not create a privileged browser/client service-role connection. Secret/server keys are limited to authorized Auth administration and controlled offline imports.

### Confirmed employee-access slice

An employee invitation must already be accepted, the identity linked and the employee active before this journey starts. Email/password sign-in and recovery do not grant employee authority. Validate the session and check live employee membership on every protected server request; ordinary application requests continue to use the user's publishable-key client and RLS, never a privileged fallback.

Application endpoints return `403` for an authenticated inactive/unlinked identity, and the UI shows localized access denied rather than an empty inventory. Direct Data API SELECTs may return zero rows under RLS instead of a permission error; guarded RPCs reject unauthorized calls. Denial must hold for subsequent requests using a JWT issued before deactivation. On the next protected request or window refocus, recheck membership and clear displayed inventory/contact data if denied; previously delivered information cannot be recalled.

The slice signs out only the current browser session, clears sensitive client state and prevents cached detail exposure through Back, refresh or protected navigation. Other device sessions remain signed in. Refresh-access revocation does not guarantee immediate invalidation of an already-issued copied access token before expiry.

Persist VI/EN preference through `set_my_locale` before switching the interface. Failure retains the previous language and shows a localized error; success preserves search query, result position and open property. Read the saved preference after subsequent login. No language change rewrites source records.

The issue #1 implementation supplies sign-in, protected browsing/search, read-only details, local sign-out and saved VI/EN preference. Real delivered password recovery has passed for active, inactive and unlinked identities through the actual UI; denied recovery neither activated nor linked the employee and did not grant inventory access. The dedicated synthetic fixture was restored. This is scoped development evidence, not full MVP or production acceptance. See the [delivery scope](delivery-plan.md#confirmed-first-employee-access-slice) and [acceptance evidence and limits](testing.md#confirmed-employee-access-slice-acceptance).

Property file read workspace (ticket #22):

Signed URLs are bearer credentials until expiry; they must not be logged, persisted in metadata or publicly cached. Renewal requires a new authorized read.
Open/download failures display the existing localized error without removing completed rows. Pending requests are aborted or ignored when their protected workspace changes; external windows use `noopener,noreferrer`.

Upload recovery (ticket #24): `GET /api/properties/{propertyId}/files/recovery` returns the current uploader's pending/failed registrations with authoritative Storage states `absent`, `present`, `unknown` or `unusable`. Optional `?fileId={uuid}` includes that uploader's completed registration to reconcile a lost response. Live membership, matching property and an unarchived parent are required. A missing-object response permits matching count/hash reselection against the same UUID/path and original metadata; existing bytes only retry completion. Unknown transport/permission outcomes never permit blind upload. Incomplete legacy expectations or unusable historical paths require a new replacement identity, never retargeting or deletion. Local bytes and transport credentials stay transient; browsers cannot restore local-file access after closure.

Recovery: `POST /api/auth/recover` `{email,locale}` invokes `resetPasswordForEmail`; `/auth/callback` exchanges a real PKCE `code` with the current SDK's optional `sb_flow_id` verifier slot, and `/auth/confirm` accepts only `token_hash` with `type=recovery`. Neither callback accepts arbitrary redirect targets. `POST /api/auth/password` `{password,confirmPassword}` requires a verified Auth user and the matching recovery-flow marker, enforces 8–128 characters/matching inputs, updates the password and signs out locally. The marker is not employee authority. Callback URLs are not printed by Next request logging. No employee row is created, linked, activated or promoted by recovery.

## Ordinary writes

Issue #7's forward source migration replaces property/address/contact/link direct writes with [transactional maintenance and business history](maintenance-contract.md). Hosted schema application and real acceptance remain pending. The following role boundaries still apply; they are enforced through revision-checked operations, not parallel CRUD.

- Active employees may create properties; the DB sets creator/updater from their session. Sales edit their own unarchived properties; staff/managers/admin can edit shared inventory.
- Manager/admin decide record-review and legal statuses. Ordinary maintenance cannot confirm or reverse a sale; that sold transition is delivered by the independent sale completion (issue #38, [below](#issue-38--independently-confirmed-sale-completion-and-completed-sale-ranking)). Sales cannot claim review approval by patching a property.
- Address writes follow property edit permission; verified mappings require manager/admin. Primary-address replacement must be atomic; the planned maintenance slice does not require a separate approver.
- Creating contacts, changing relationship/primary markers and removing links require staff/manager/admin. Correcting the details of an existing linked shared contact is available to every active employee on a readable property, independent of property-fact edit authority, provided an ordinary employee's target is linked to the opened property. Unlinking retains the shared contact and other links; same-person corrections append history to every affected property, and unlinked-identity correction stays staff/manager/admin-only.
- Files: no direct authenticated metadata INSERT/UPDATE/DELETE. Registration and attested completion use invoker RPC wrappers around narrowly granted private definers. Historical review data is retained; review mutation RPCs are removed.
- Employee rows are provisioned only through the owner/administrative path (or a future guarded operation); direct client lifecycle, sign-in-link and role writes are refused by the guard, and the client insert/update policy and grant remain only for that future operation. Creating an employee row does not create an Auth user; invitations and confirmed account linkage are separate server operations. Admin also maintains official catalogs.
- Hard deletes are not exposed. When deactivating an employee, review their approved locks and release or let them expire; deactivation blocks new employee DB requests but does not erase attribution history.

## Private audit trail retention

`private.audit_events` is the append-only evidence trail: `private.audit_change()` fires `after insert or update or delete` on the audited public tables and records the authenticated actor (`auth.uid()`), the table, the record key, the action, the full before/after `jsonb` snapshot and the server time. It is unexposed and revoked from `anon`/`authenticated`; no application endpoint, view or report returns it, so it is evidence rather than inventory data and no caller ever sees audit content. That guarantee is unchanged for every row inside the retained window.

The trail is also the largest table in the database and the only one that grows on its own. Forward migration `20261015152708_audit_trail_retention.sql` adds one deliberate retention rule for it:

- **Window.** A row is retained while `created_at >= now() - 365 days`; only rows older than that are eligible. `365` is the default and lives in exactly one place — the `p_retain_days` default of `private.trim_audit_events`. Nothing inside the window is ever removed, the trail is never disabled or paused for the retained period, and the rule touches no other table: `public.property_history` and every business record keep their own lifecycle.
- **Mechanism and caller.** `private.trim_audit_events(p_retain_days integer default 365, p_max_rows integer default 20000) returns integer` deletes the oldest eligible rows, at most `p_max_rows` per call, and returns how many it removed (`0` means nothing is currently eligible). The database owner runs it from a privileged SQL session, the same plane that applies migrations: `select private.trim_audit_events();`. This project has no scheduler (no `pg_cron`, no Vercel cron entry, `git.deploymentEnabled` is false), so retention is an explicit, documented administrative action rather than an automatic job; repeat the call until it returns `0`. EXECUTE is revoked from `public`, `anon`, `authenticated` and `service_role`, so no application, API or trusted-server role can delete audit evidence, and no new endpoint is added.
- **One table only.** The target table is written literally into the function, which takes no table identity and holds no dynamic SQL; it cannot be pointed at another table. A window outside `30`–`3650` days or a row cap outside `1`–`1000000` is refused with `22023` rather than guessed, so the floor always keeps at least 30 days and a bad value cannot become a wipe. Change the window per call (`select private.trim_audit_events(180)`) or change the default in a later forward migration.
- **Index.** `audit_events_created_at_idx` serves the window filter, so the trim reads the oldest rows instead of scanning and sorting the whole trail.
- **Size effect, measured.** Deleting rows frees space for reuse but does not shrink the relation by itself; reclaiming it to the OS needs `VACUUM FULL` in a maintenance window, which is an operator step and never part of a migration. Measured in the embedded schema over 2,600 synthetic rows shaped like this table's payloads (4,296 KB): trimming the 1,300 rows outside the window left 4,296 KB allocated until a plain `VACUUM` made the space reusable (1,300 replacement rows then cost about 48 KB instead of about 2,150 KB) and `VACUUM FULL` rewrote the relation to 4,288 KB. The effect of this rule is therefore a bounded ceiling on an unbounded trail plus reusable space, not an immediate file shrink.
- **Verification.** `scripts/audit-retention-contract.mjs` runs in the embedded schema harness (`npm run test:schema`) for the window boundary, repeat and batch safety, the refused values, the own-table/no-dynamic-SQL binding, the employee/anon/service-role denial and continued recording after a trim. The hosted trim and its measured effect on a real project remain staging gates ([testing.md](testing.md#private-audit-trail-retention-acceptance)).

## Document protocol

1. Choose one client UUID per file before registration. Register its safe original filename, supported MIME, positive byte count ≤20 MiB, SHA-256 and document/photo purpose. New registrations use `<property_uuid>/<file_uuid>/content`, an opaque ASCII Storage key; original filenames remain verbatim metadata and download names. Existing paths, expectations and attribution are immutable.
2. `POST /api/properties/{propertyId}/files/register` returns `{fileId,objectPath,uploadUrl,publishableKey,accessToken}`. The request validates the live employee before obtaining the session JWT solely for direct upload transport.
3. POST bytes directly to private Storage with that user's JWT and `x-upsert: false`. This avoids Vercel's request-body limit while retaining Storage's live employee/pending-owner policy; no bearer signed-upload token or service-role upload is used. Keep transport credentials only in memory.
4. `POST /api/properties/{propertyId}/files/{fileId}/complete` accepts only `{}`. It inspects and downloads the actual object through the user's session, checks its immutable identity, exact bytes/hash and decoded supported format, and signs a versioned HMAC attestation. The database independently verifies the signature, original expectations, object identity and current actor after locking the parent property then file. An arbitrary browser RPC cannot mark a file ready.
5. Each open/download requests a fresh 60-second signed URL after live access checks. Already-issued bearer URLs remain usable until expiry; subsequent issuance and metadata/byte reads are denied after deactivation.
6. Registration and completion retry the same UUID/path. Existing bytes are never overwritten; replacement requires a new UUID/path. A transport failure is not proof of missing bytes.

Bucket enforcement limits objects to 20 MiB and PDF/JPEG/PNG/WebP. Image validation decodes actual image content; PDF validation requires its header/EOF and parses its object graph/page tree using pinned `pdf-lib`. This is not semantic/legal authenticity checking, malware scanning or human review. Historical ready rows remain readable with original IDs, paths, expectations and review attribution.

Install one cryptographically random 32-byte hex key as server-only `SGN_FILE_VALIDATION_KEY` and the matching `private.file_validation_keys` singleton (`id=1`) through the database owner. Neither authenticated clients nor service_role have key-table privileges. Missing configuration fails closed. Never commit, expose through `NEXT_PUBLIC_`, print or return this key. Migration SQL contains no secret.

## Types and error behavior

- IDs are UUID strings; source spreadsheet IDs are provenance only.
- Prices are whole-VND decimal strings at JSON boundaries; avoid JS floating-point conversion or exceeding safe integer precision. UI accepts/display tỷ/triệu but persists canonical VND.
- Timestamp values are ISO 8601 UTC instants. Source naive timestamps are interpreted in Vietnam only after confirming this assumption.
- `42501`: permission/role failure → show access denied. `23505`: duplicate pending request or reservation conflict → refetch current state. Check errors/invalid transitions → actionable validation message. Other failures → generic error plus protected diagnostics.
- Do not expose database stack traces, raw audit payloads or customer documents in logs.

### Issue #66 — Guarded employee deactivation

Migration `20261013161609_employee_admin_deactivation.sql` adds the durable administration operation, its append-only evidence, the last-active-admin guard and the two guarded RPCs. Deactivation disables membership first and completes only after the exact Auth sign-in block is confirmed through a server-only adapter; the employee, locale, Auth link, reservations, activity, files and history are never rewritten, and nothing transfers a reservation.

- **`employee_admin_operations`**: one row per attempted employee administration action with the target, the acting admin, `kind` (`deactivate`/`delete`), the actor-scoped `idempotency_key`, `state` (`provider_pending`/`provider_failed`/`completed`), a monotonic `revision`, the recorded provider outcome/reference/detail and the membership-disabled time; a deactivation adds `provider_ban_until`/`provider_user_id` and a deletion adds the locked `target_auth_user_id`, the `storage_owned_count`, the `storage_reassigned_count` and `provider_user_id`. `(actor_id, idempotency_key)` is the retry identity; a partial unique index keeps at most one open operation per employee, so a competing deactivation and deletion cannot both proceed, while a completed operation stays as history. The table grants `select` only, under a live-admin RLS policy; no client INSERT/UPDATE/DELETE grant exists and a guard trigger refuses direct writes and any identity rewrite.
- **`employee_admin_events`**: append-only evidence (`begun`, `resumed`, `provider_blocked`, `provider_failed`, `provider_ambiguous`, and for deletion `storage_blocked`, `account_deleted`) with the acting admin and a bounded detail. A resuming admin's submission key is bound here to the operation it resumed (unique per actor and key), so a lost-response retry returns the original result for that actor and key. It grants `select` only under the same live-admin policy, and its guard rejects every non-INSERT and every client write. Both tables feed the existing `private.audit_events` trail.
- **Last-active-admin protection** is a trigger on `public.employees`. A client-role (`anon`, `authenticated`, `service_role`) lifecycle, sign-in-link or role write is refused at the guarded boundary with `42501` before the check runs; an owner/administrative writer that reaches the check raises `P0010` when an update or delete would leave no other active admin, serialized by an advisory lock so two concurrent removals cannot both pass. It covers deactivation, role demotion, unlink (which the table check already forces to inactive) and deletion. Locale is not a lifecycle field, so `set_my_locale` remains valid.
- **`begin_employee_deactivation`** is a public invoker wrapper over a private definer. It re-reads the live role (`admin` only), locks the target employee row then the open operation, converges an initiating or resuming same-actor/key retry on the original operation (including after the operation completed), rejects a different employee/action under the same key with `23505`, resumes any open operation for a currently authorized admin without rewriting its actor, refuses an unlinked target (`P0011`) or an already-inactive target without an open operation (`P0011`), opens the operation and then disables membership in the same transaction, so a refused last-admin removal rolls back without leaving a claim that membership was disabled. The projection returns the state, revision and recorded provider fields.
- **`record_employee_deactivation_result`** is executable only by `service_role`; its public wrapper and the private definer are revoked from `public`/`anon`/`authenticated`. It locks the employee row then the operation, verifies the presented revision (`PT409` when stale), verifies the presented Auth user id equals the employee's current `auth_user_id` (`P0012` otherwise, so a relinked identity is never reported as the blocked one), requires a provider reference and `banned_until` for `blocked`, records `provider_failed` for `failed`/`ambiguous`, and treats `completed` as terminal while an identical confirmed retry converges. A detail longer than 500 characters, an invalid outcome or a missing recording actor is `23514`.
- **Ban limitation**: the adapter requests a finite GoTrue ban (`876000h`, about 100 years) and stores the provider's own `banned_until`; renewal happens only through an explicit reconciliation and the block does not delete or disable the identity, so it is never described as an infinite state. The hosted check must confirm the deployed Auth version returns `banned_until` (see the testing plan).
- **Application boundary**: `GET /api/employees/{id}/deactivation` returns the target identity, the latest recorded deactivation operation and the outstanding reservations (approved-unexpired effective, pending requests, with expiry); `POST /api/employees/{id}/deactivation` accepts exactly `{key: UUID}`, re-reads live admin membership, calls the guarded begin, then the server-only adapter ban, then the server-only result RPC, re-reads live membership after that provider transition (so an admin who deactivated their own row receives `403 access-denied` rather than a `404` load failure), and returns the fresh confirmation. Responses stay `private, no-store`; the browser never supplies the actor, target Auth identity, outcome or revision. A missing server secret leaves the operation open as `provider_pending` and answers `503/provider-unavailable` rather than claiming anything about authentication. `GET /api/employees` attaches the recorded operation state to each row so the list separates confirmed deactivation from reconciliation.
- **Outstanding reservations**: the confirmation reads the recorded rows under existing RLS. Effective reservations and pending requests stay attributed to the departing employee; the control only makes their existence visible, and the existing claimant/reviewer release and expiry rules remain the only ways they close. No disposition, transfer or attribution rewrite is baked into deactivation. The same read backs the account-deletion confirmation, which removes access the same way.

### Issue #67 — Permanent sign-in-account deletion with the retained employee

Migration `20261015070349_employee_account_deletion.sql` adds the second lifecycle kind on the same operation ledger. Deletion disables membership and clears the restrictive sign-in link first, preflights and reassigns Storage ownership to a live active admin custodian, and completes only after the provider account is confirmed absent. The retained Employee UUID/name/role/locale, every business foreign key, every uploader attribution and the historical Auth identifier survive; nothing repoints a foreign key to the acting admin, cascades an Employee delete, erases private audit or deletes a document.

- **`employees.account_deleted_at`**: the retained account lifecycle state, set once when the deletion is confirmed.
