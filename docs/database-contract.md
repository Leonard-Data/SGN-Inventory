# Database contract for the Next.js application and coding agents

Contract version: `0.3.0`; SQL schema authority: `supabase/migrations/`. Single company, invite-only employees, public Data API schema + unexposed private internals.

## Mandatory localization and rentals

Vietnamese (`vi`, default) and English (`en`) are both required in the application. Keep Vietnamese regional data conventions in either language; persist `employees.preferred_locale` through `set_my_locale`. UI language and signed rental document language are separate.

Rental lifecycle, monthly occupancy/dues and manual payment receipt/refund tracking are in scope. Use the normative [rental and localization contract](rental-localization-contract.md) for schemas, RPC parameters, status labels, authorization and acceptance rules. This adds rent tracking, without commission payouts or a payment gateway.

## Client and authorization contract

Use the signed-in user's request-scoped Supabase client with the publishable key. DB helpers find an **active** employee whose `auth_user_id = auth.uid()`. Application roles are stored in `employees.role`, not `user_metadata`. A signed-in Auth user without an active employee row has no inventory access.

Expose only `public` in the Data API. `private` must remain unexposed even though authenticated DB roles have USAGE and narrowly scoped helper EXECUTE permissions. Do not create a privileged browser/client service-role connection. Secret/server keys are limited to authorized Auth administration and controlled offline imports.

### Confirmed employee-access slice

An employee invitation must already be accepted, the identity linked and the employee active before this journey starts. Email/password sign-in and recovery do not grant employee authority. Validate the session and check live employee membership on every protected server request; ordinary application requests continue to use the user's publishable-key client and RLS, never a privileged fallback.

Application endpoints return `403` for an authenticated inactive/unlinked identity, and the UI shows localized access denied rather than an empty inventory. Direct Data API SELECTs may return zero rows under RLS instead of a permission error; guarded RPCs reject unauthorized calls. Denial must hold for subsequent requests using a JWT issued before deactivation. On the next protected request or window refocus, recheck membership and clear displayed inventory/contact data if denied; previously delivered information cannot be recalled. `GET /api/session` returns `{employee{id,displayName,role,locale},accessRevision}`, the employee's monotonic `employees.access_revision`. A protected read authorizes on identity, role and that revision, reads the session before its data and again after it, and clears the displayed surface rather than publishing or keeping data authorized on a superseded access; an unchanged revision keeps the surface. A read whose revision keeps advancing stops after three attempts with a localized notice that access changed and the page must be reloaded. The revision advances when the role, activation state or sign-in link changes and stays put on every other edit, and no client chooses it.

The slice signs out only the current browser session, clears sensitive client state and prevents cached detail exposure through Back, refresh or protected navigation. Other device sessions remain signed in. Refresh-access revocation does not guarantee immediate invalidation of an already-issued copied access token before expiry.

Persist VI/EN preference through `set_my_locale` before switching the interface. Failure retains the previous language and shows a localized error; success preserves search query, result position and open property. Read the saved preference after subsequent login. No language change rewrites source records.

The issue #1 implementation supplies sign-in, protected browsing/search, read-only details, local sign-out and saved VI/EN preference. Real delivered password recovery has passed for active, inactive and unlinked identities through the actual UI; denied recovery neither activated nor linked the employee and did not grant inventory access. The dedicated synthetic fixture was restored. This is scoped development evidence, not full MVP or production acceptance. See the [delivery scope](delivery-plan.md#confirmed-first-employee-access-slice) and [acceptance evidence and limits](testing.md#confirmed-employee-access-slice-acceptance).

`GET /api/properties` accepts `query`, `page`, `status`, `mode`, `type`, `priceMin`, `priceMax`, `areaMin`, `areaMax`, `province`, `ward`, and `contact`; chronological views additionally accept `sort=oldest|newest`. `page` is a positive integer in the address and is refused (`400/invalid-input`) when non-numeric or zero, never served as a different page; the page size is fixed at 30 rows, and any other search parameter (including `pageSize`) is refused the same way. The response states the matching `total` beside the served `page`. `province`/`ward` are official `admin_unit_versions` IDs (`province` level and `commune` level), matched against a property's recorded address units; the ward is dependent on the province and, when both are set, the narrower ward is the unit applied. `contact` is a recorded Contact ID matched through the `property_contacts` link, refused (`400/invalid-input`) when malformed or when it names no readable contact, exactly as an out-of-catalog area unit is refused; it composes with every other filter and applies the ordinary unarchived inventory boundary. The contact-directory count is pinned to the same caller's unarchived readable links, so the count and this filter can never disagree about one person.

`src/lib/supabase/route.ts` creates one publishable-key/session client per request, forwards refreshed cookies and SDK cache headers, and applies private/no-store responses and no-referrer policy. Auth cookies are HttpOnly and Secure on HTTPS. The locale cookie is presentation only; live membership and employee preference come from the database. Public auth navigation may carry `lang=vi|en`, but successful protected language switching persists only through `set_my_locale`.

Application endpoints: `POST /api/auth/login` `{email,password,locale}`, `POST /api/auth/logout` `{}` (local scope), `GET /api/session`, `GET /api/properties?query=&page=&sort=&status=&mode=&type=&priceMin=&priceMax=&areaMin=&areaMax=&province=&ward=&contact=`, `GET /api/properties/[id]`, `POST /api/properties/[id]/page-view` `{key}`, `POST /api/properties/[id]/owner-contact` `{key}`, `GET`/`POST /api/properties/[id]/vendors`, `POST /api/properties/[id]/vendors/[vendorId]`, `GET /api/activity/today`, `GET /api/activity/me?from=&to=`, `GET /api/activity/company?from=&to=`, `GET /api/activity/provinces?from=&to=`, `GET`/`POST /api/properties/[id]/comments`, `GET`/`PATCH /api/properties/[id]/comments/[commentId]`, `POST /api/properties/[id]/comments/[commentId]/removal`, `GET /api/properties/[id]/comments/[commentId]/history`, `GET`/`POST /api/properties/[id]/reservations`, `POST /api/properties/[id]/reservations/decision`, `POST /api/properties/[id]/reservations/release` `{lockId,reason}`, `GET`/`POST /api/properties/[id]/sale-completion`, `GET /api/reports/completed-sales?from=&to=`, `GET /api/employees?after=`, `GET`/`POST /api/employees/invitations` (`{email,role,key}`), `POST /api/auth/invite/session` (`{accessToken,refreshToken}` or `{}`), `POST /api/auth/invite/accept` (`{invitationId,revision,name,password,confirmPassword,locale}`), `GET /api/vendors?query=&before=&beforeId=`, `POST /api/vendors` `{key,displayName,contactName?,phones?,email?,sourceAddress?,notes?}`, `GET /api/vendors/[id]`, and `POST /api/locale` `{locale}`. All JSON writes require the configured same Origin and a bounded JSON object; identities, keys, enum values and query bounds are validated. Issue #7 adds same-origin creation/maintenance, contact, correction, amendment and property-history endpoints under the same rules; issue #36 adds `GET /api/properties/[id]/price-history?series=sale|rent&before=&beforeId=` over the same property-scoped history boundary and an optional maintenance `explanation` for an authorized price correction; see [maintenance-contract.md](maintenance-contract.md). Detail prices are cast to text in PostgREST before JSON serialization; consumers must keep whole-VND decimal strings, not parse them to Number.
Property file read workspace (ticket #22):
- `GET /api/properties/{propertyId}/files` → `{files: [...]}` — completed attachments for a property, subject to live employee access and archived-property reviewer boundary.
- `POST /api/properties/{propertyId}/files/{fileId}/signed` `{download?: boolean}` → `{url, expiresAt}` — authorized 60-second presigned R2 GET URL; the record is read first under RLS. Omission means open; non-boolean values and unknown keys return `400/invalid-input`. Downloads retain the original filename through `response-content-disposition`.
Signed URLs are bearer credentials until expiry; they must not be logged, persisted in metadata or publicly cached. Renewal requires a new authorized read.
Open/download failures display the existing localized error without removing completed rows. Pending requests are aborted or ignored when their protected workspace changes; external windows use `noopener,noreferrer`.

Upload recovery (ticket #24): `GET /api/properties/{propertyId}/files/recovery` returns the current uploader's pending, failed and `cleanup_pending` registrations with the private bucket's states `absent`, `present`, `unknown` or `unusable`. Optional `?fileId={uuid}` includes that uploader's completed registration to reconcile a lost response. Live membership, matching property and an unarchived parent are required. A missing-object response permits matching count/hash reselection against the same UUID/path and original metadata; existing bytes only retry completion. An unreachable or unconfigured store is `unknown`, never `absent`, so an outage can never be read as permission to upload over existing bytes. The list form also discards the bytes of a registration still `pending` after the 15-minute upload window and reports it `absent` once the removal succeeded (`unknown` if it failed); the row itself stays and reselection reuses its UUID/path. A `cleanup_pending` registration is reported `unusable`/`replacement-required` and makes no R2 call from this read: its bytes are deleted by the server-side cleanup pass below, whatever the parent's archived state and whether or not its uploader returns. Incomplete legacy expectations require a new replacement identity, never retargeting or deletion. Local bytes stay transient; browsers cannot restore local-file access after closure.

Recovery: `POST /api/auth/recover` `{email,locale}` invokes `resetPasswordForEmail`; `/auth/callback` exchanges a real PKCE `code` with the current SDK's optional `sb_flow_id` verifier slot, and `/auth/confirm` accepts only `token_hash` with `type=recovery`. Neither callback accepts arbitrary redirect targets. `POST /api/auth/password` `{password,confirmPassword}` requires a verified Auth user and the matching recovery-flow marker, enforces 8–128 characters/matching inputs, updates the password and signs out locally. The marker is not employee authority. Callback URLs are not printed by Next request logging. No employee row is created, linked, activated or promoted by recovery.

Paged inventory parameters, one read for both orderings: `p_order text=NULL` (`NULL` is the ordinary browse, `oldest`/`newest` the eligible chronology), `p_query text=''`, `p_page integer=1`, `p_page_size integer=30` (clamped to at most 50), then the same `p_status text=NULL`, `p_mode text=NULL`, `p_type text=NULL`, `p_price_min numeric=NULL`, `p_price_max numeric=NULL`, `p_area_min numeric=NULL`, `p_area_max numeric=NULL`, `p_area_id uuid=NULL` and `p_contact_id uuid=NULL` filters for both. The ordering, page number, query length and filter bounds are validated (`22023`); an inaccessible session raises `42501` on the chronological order. The function derives the Vietnam business day in the database, so age and ordering never follow a browser timezone. Empty query browses inventory; query text over 120 characters is refused (`22023`) rather than read as empty inventory. `p_mode='sale'` or `'rent'` also includes `both`. `p_area_id` matches a province, district or commune version ID on any address; the route resolves the page's `province`/`ward` selection to the narrower unit and refuses a malformed, out-of-catalog, wrong-level or wrong-province value (`400/invalid-input`). `p_contact_id` matches a property whose readable `property_contacts` link names the given contact, in the same bounded read (no per-row round trip); the route refuses a malformed or unreadable contact ID (`400/invalid-input`) rather than treating it as an unlinked contact with no matches. For unresolved raw legacy labels, apply a separately validated label filter when the UI is implemented; never equate a text match with a verified current-area ID.

The SQL paged response carries `total_count`, `page_number` and the page's rows, so the matching total and the rows always come from the same filtered statement. The ordinary browse is ordered by UUID ascending and the chronology by recorded entry date then identity with unknown dates last; both are total orders, and `p_page_size` is clamped to at most 50 rows. A page past the end is corrected to the last page of that same result set and reports the page it served; a filtered set with no match returns no rows and a total of zero. Fetch result address summaries separately by the returned property IDs; bound relation queries to the current page. The status, mode and type filters are ordinary equality on the property row, each optional bound is whole VND or m², and an out-of-range or reversed bound is refused (`22023`) rather than matched: with no listing mode selected, price uses each listing's own asking price (monthly asking rent for rentals, whole-VND asking sale price for sale and sale-and-rent listings); selecting Sale or Sale-and-rent compares asking sale price, while selecting Rent compares monthly asking rent; area matches the land area or the floor area. Do not interpolate user SQL.

Address search is accent-insensitive contiguous-substring matching with literal `%`, `_` and backslash, not fuzzy or reordered-token matching. Forward migration `20261015173132_address_search_official_units.sql` includes selected official unit names in `search_text`, so a dropdown-only address remains searchable even when no source label was recorded. `20261010073738_literal_inventory_search.sql` escapes patterns without rewriting the deployed foundation migration, applies the 120-character bound to raw input and retains UUID ordering/RLS/default limits. Show the matching recorded address format and verification state; never infer a verified ward from a text match.

## Private audit trail retention

`private.audit_events` is the append-only evidence trail: `private.audit_change()` fires `after insert or update or delete` on the audited public tables and records the authenticated actor (`auth.uid()`), the table, the record key, the action, the full before/after `jsonb` snapshot and the server time. It is unexposed and revoked from `anon`/`authenticated`; no application endpoint, view or report returns it, so it is evidence rather than inventory data and no caller ever sees audit content. That guarantee is unchanged for every row inside the retained window.

The trail is also the largest table in the database and the only one that grows on its own. Forward migration `20261015152708_audit_trail_retention.sql` adds one deliberate retention rule for it:

- **Window.** A row is retained while `created_at >= now() - interval '90 days'`; only rows older than that are eligible. The 90-day interval is held in one internal constant in `private.trim_audit_events()`. Nothing inside the window is ever removed, the trail is never disabled or paused for the retained period, and the rule touches no other table: `public.property_history` and every business record keep their own lifecycle.
- **Mechanism and caller.** `private.trim_audit_events()` returns the number of eligible rows it deletes (`0` means nothing is currently eligible). The database owner runs it from a privileged SQL session, the same plane that applies migrations: `select private.trim_audit_events();`. This project has no scheduler (no `pg_cron`, no Vercel cron entry, `git.deploymentEnabled` is false), so retention is a deliberate administrative action rather than an automatic job; a repeat run is safe and returns `0` once no older rows remain. EXECUTE is revoked from `public`, `anon`, `authenticated` and `service_role`, so no application, API or trusted-server role can delete audit evidence, and no new endpoint is added.
- **One table only.** The target table is written literally into the function, which is parameterless and holds no dynamic SQL; it cannot be pointed at another table. Supplying a table identity is refused by the function signature rather than interpreted as a different target.
- **Index.** `audit_events_created_at_idx` serves the window filter, so the trim reads the oldest rows instead of scanning and sorting the whole trail.
- **Size effect, measured.** Deleting rows frees space for reuse but does not shrink the relation by itself; reclaiming it to the OS needs `VACUUM FULL` in a maintenance window, which is an operator step and never part of a migration. Measured in the embedded schema over 2,600 synthetic rows shaped like this table's payloads (4,296 KB): trimming the 1,300 rows outside the window left 4,296 KB allocated until a plain `VACUUM` made the space reusable (1,300 replacement rows then cost about 48 KB instead of about 2,150 KB) and `VACUUM FULL` rewrote the relation to 4,288 KB. The effect of this rule is therefore a bounded ceiling on an unbounded trail plus reusable space, not an immediate file shrink.
- **Verification.** `scripts/audit-retention-contract.mjs` runs in the embedded schema harness (`npm run test:schema`) for the 89-day retained / 91-day eligible boundary, repeat safety, refusal of a supplied table identity, another private table left untouched, the employee/anon/service-role denial and continued recording after a trim. The hosted trim and its measured effect on a real project remain staging gates ([testing.md](testing.md#private-audit-trail-retention-acceptance)).

## Document protocol

1. Choose one client UUID per file before registration. Register its safe original filename, supported MIME, SHA-256 and document/photo purpose, plus its exact byte count. Content class decides the caps, never the chosen purpose, category or cover choice: a PDF is a document and JPEG/PNG/WebP are images. Per property that means **at most 5 documents of at most 20 MiB each** and **at most 10 images of at most 5 MiB each**, the property cover included. New registrations use `<property_uuid>/<file_uuid>/content`, an opaque ASCII object key; original filenames remain verbatim metadata and download names. Existing paths, expectations and attribution are immutable.
2. `POST /api/properties/{propertyId}/files/register` returns `{fileId,objectPath,uploadUrl,uploadBytes}`. The route validates the live employee and the class size cap, and the registration transaction (behind the parent property row lock) enforces the class size and count caps before any URL exists, so a refusal leaves no partial state. `uploadUrl` is a 60-second presigned R2 `PUT` for that exact key whose signature covers `content-length` and `if-none-match`, so R2 itself refuses any body whose length differs from `uploadBytes` (the registered byte count, already at most the class cap of 20 MiB for a document or 5 MiB for an image) and refuses to replace an existing object.
3. The browser `PUT`s exactly those bytes straight to the private R2 bucket with the matching `content-length` and `If-None-Match: *` headers. The application server never streams file bytes in either direction, and no Storage JWT, publishable key or service-role credential reaches the browser.
4. `POST /api/properties/{propertyId}/files/{fileId}/complete` accepts only `{}`. It reads the object's metadata and bytes from R2 with server-only credentials, re-checks the class size cap against the actual bytes, checks its immutable expectations, exact bytes/hash and decoded supported format through `content.ts`, and signs a versioned HMAC attestation over the object identity. The database independently verifies the signature, original expectations, the class count cap and the current actor after locking the parent property then file. An arbitrary browser RPC cannot mark a file ready. R2 is not visible to the database, so the attestation is the evidence that this exact object was inspected; the `property_files` row remains the authority for who may read it.
5. Each open/download requests a fresh 60-second presigned URL after live access checks. Already-issued bearer URLs remain usable until expiry; subsequent issuance and metadata/byte reads are denied after deactivation. An archived property still hides its files from everyone except a reviewer, exactly as before.
6. Registration and completion retry the same UUID/path. Completion converges on an already-ready file; different bytes under the same registration are refused as a mismatch. Replacement requires a new UUID/path. A transport failure is not proof of missing bytes.

The bucket is private and reached only through presigned URLs; `R2_ACCOUNT_ID`, `R2_BUCKET`, `R2_ACCESS_KEY_ID` and `R2_SECRET_ACCESS_KEY` are server-only environment variables, and a missing value fails the file operation closed with an opaque `503` while the server log names it, instead of falling back to Supabase Storage. The class caps are enforced at registration and re-checked at completion; a pending registration reserves its slot, so concurrent uploads cannot overshoot the limit, and property rows that already exceed a cap (imported or legacy data) simply accept no further file of that class. The per-file size cap is also enforced where the bytes are written: the signed `PUT` covers the registered byte count and the conditional create, so only that exact body can ever be stored — never more than the class cap — and an existing object is never replaced, which is what makes "existing files are never overwritten" a signature-enforced rule rather than a promise. A refused completion (`400`) releases that uploader's pending registration to `cleanup_pending` through `public.fail_property_upload` — the class slot is free at once — only when that release reports it moved the row, then deletes the stored object and only then records `failed` through the server-only `public.mark_upload_cleaned`, so `failed` always means the bytes are gone and the row is retained as evidence. A removal that fails leaves the row `cleanup_pending`, which is not `failed` and takes no new upload. The server-side cleanup pass is what retries it: it selects every `cleanup_pending` registration regardless of the parent's archived state, of who uploaded it and of whether anyone visits that property, deletes each object and only then records `failed`, reading and writing through the server-only service-role client that ordinary requests never expose. It runs from two places because this deployment has no scheduler: `POST /api/maintenance/file-cleanup`, the operator action authenticated with the server-only service key, processes up to 20 released registrations per call, and every server file-completion request opportunistically processes up to 3 more so ordinary traffic drains the backlog. Each run is bounded, and it logs how many it retried, how many it cleared and how many remain, so a repeatedly failing removal stays a visible, retried backlog rather than a silent orphan. The recovery list also discards the bytes of a registration still `pending` after 15 minutes, which is the same window the class-slot count excludes, because the signed URL has expired by then. Registration mints an upload signature only for a row that is still `pending`, so a released or finished registration can never collect new bytes outside those cleanup paths. A ready file's bytes are never deleted by any path. Image validation decodes actual image content; PDF validation requires its header/EOF and parses its object graph/page tree using pinned `pdf-lib`. This is not semantic/legal authenticity checking, malware scanning or human review. Historical ready rows remain readable with original IDs, paths, expectations and review attribution.

Install one cryptographically random 32-byte hex key as server-only `SGN_FILE_VALIDATION_KEY` and the matching `private.file_validation_keys` singleton (`id=1`) through the database owner. Neither authenticated clients nor service_role have key-table privileges. Missing configuration fails closed. Never commit, expose through `NEXT_PUBLIC_`, print or return this key. Migration SQL contains no secret.

Moving existing objects to R2, and file retention. Forward migration `20261018031541_property_file_storage_limits.sql` adds the class caps and drops the database's former Supabase Storage object-existence check, which cannot apply to a private R2 bucket; the identity evidence is now the server's signed attestation over the object it read from R2. `scripts/copy-property-files-to-r2.mjs` copies every registered object from the Supabase `property-files` bucket to R2 with identical keys, so no `property_files` row is rewritten: it is a dry run by default, `--apply` copies and then verifies, `--verify` runs only the verification pass, and the verification compares the registered key set against the bucket listing and every recorded object size, treating a legacy row with no recorded size as present once its object exists. It reports a size conflict instead of overwriting, never deletes anything in Supabase, and has not been run against a hosted project; retiring the old bucket is a separate deliberate operator action. File records are retained: no user-facing or RPC path deletes a `property_files` row and `authenticated` holds no INSERT/UPDATE/DELETE grant on the table, so removing a cover choice, recategorizing a file or replacing your own attachment never removes the original row. Ready files are retained together with their objects; only the bytes of a refused upload (`cleanup_pending`) or of an expired pending registration are deleted, and the row that records them stays. Any future deletion path must delete the R2 object in the same operation as the row.

### Issue #147 — shared-address group and duplicate merge

`20261018140606_property_address_duplicate_merge.sql` adds two read-and-write surfaces and no table. A record whose primary address is shared states how many other records carry it, opens a side-by-side comparison, and offers two outcomes: keep both, which changes nothing at all, or merge, which is a deliberate manager/admin action.

- **Address equality.** Membership is `private.address_match_key`, which is `private.normalize_search` (lowercased, accent-folded) over the recorded `address_text` of the primary address — the same normalisation inventory search already uses. No second, fuzzy or reordered-token matcher is introduced, and the address model is untouched.
- **Most complete record.** `private.property_completeness` counts recorded facts, owner links, readable files and recorded history. The survivor is the highest count, then the earliest `created_at`, then the lowest `id`; both the read and the merge apply that exact order, and a merge that names a different target is refused (`P0008`) rather than silently retargeted.
- **What moves.** Owner links (`property_contacts`, with at most one becoming the survivor's primary contact and a pair the survivor already records converging on that one link), `property_history` rows (the retained change trail behind the asking-price series), and every ready `property_files` row. A merged-away cover is cleared and adopted by the survivor only when it has none. The folded records are then archived, which is the same retained-review state as any archived property, so their comments, locks, corrections, activity and rental-adjacent records stay readable evidence on the retired record rather than being deleted. Nothing is hard-deleted.
- **File bytes.** A file record's `object_path` is bound to `property_id`, so a move changes the key. The server copies each ready object to the survivor's key with a same-bucket `CopyObject` before the database transaction, then passes the copied ids as `p_moved_file_ids`; the merge refuses when a ready file is missing from that list (`P0016`) and the browser-side route removes its copies if the merge is refused, so a half-moved file is never recorded. `private.guard_file_identity` keeps refusing every ordinary client identity change and admits exactly the merge path, where the merge sets its own transaction-local marker after checking the role.
- **Boundaries.** The merge is a `private` definer over a `public` invoker wrapper with explicit grants, a fixed search path, a live active-employee check and the role check; the group read is a `public` invoker function, so ordinary RLS applies and no read is widened. Anonymous, unlinked, inactive, sales and staff callers are refused `42501`. A record with an effective reservation or an active rental agreement is not merged away (`P0014`/`P0015`), because that is somebody's practical agreement rather than a duplicate record.
- **Creation is unchanged.** Nothing runs on create, no uniqueness constraint is added and a second property at an existing address remains an ordinary case; the indicator is the only new surface, and it never blocks a write.
