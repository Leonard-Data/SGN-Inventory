# Browser property catalogue and local address search

Status: accepted (2026-10-20)

Ordinary address search read the database. The list carried the free-text query in its address and every submitted search was a window of a server read (`stream_inventory`), so a remount or a return from a property's details read the same rows again. Salespeople search mostly by free text address, and caching individual search strings buys little: every spelling, abbreviation and partial address is a different key.

We decided the browser holds a compact, user-scoped catalogue of the authorized inventory and searches it locally. An authenticated Route Handler, `GET /api/properties/catalogue`, answers one bounded page of property summaries in a stable property-identity order, with each property's stored address variants flattened into its own row and money and measurements cast to text. The read runs on the caller's own session client, so Row Level Security is what decides which rows and fields exist for them at all, and it is reapplied on every page: the cursor (`after`) is a position in that one ordering and never an authorization grant. Responses stay private and `no-store`. The shared protected-session lifecycle brackets the catalogue read with live session checks and owns publication, cancellation and refocus checks. TanStack Query deduplicates the read and holds the browser cache under one key per authorized context (employee identity and role, the server-maintained `accessRevision`, and the summary's own schema version), with `staleTime`/`gcTime` at infinity and no automatic query refetch. A changed scope removes the former entry; superseded responses are discarded, and consumers only accept a catalogue matching their own protected session. A local index folds each property's recorded addresses once per loaded page and keeps the original text for display; typing in the address box narrows those rows in the browser and issues no request while the result is the loaded catalogue, while submitting the box still runs the existing server search over the whole inventory.

The loader and cache are mounted once in the shared authenticated layout, so the list and a property's details reuse one catalogue instead of each reading their own. The browser is the single initial loading owner: the list's server-rendered shell reads no catalogue at all, so nothing is fetched twice and no employee-specific result passes through a shared cache. The catalogue is a browsing snapshot. Locking, approvals and edits always validate against current server state, and a locally filtered list states what it is - the loaded catalogue, never the whole inventory.

The deliberate Refresh ([#190](https://github.com/Leonard-Data/SGN-Inventory/issues/190)) builds a replacement catalogue as a second generation instead of mutating the one in use. The working catalogue stays searchable - searched, filtered, sorted and paged - for the whole duration, and the refresh line reports the replacement's own progress separately from the working catalogue's last synchronization time. Only a replacement whose every cursor has been traversed and every received row indexed is swapped in, after the shared protected read confirms unchanged identity, role and access revision. The finished replacement is written back as the cached catalogue for the scope, so every catalogue-answered result - the ordinary browse, a supported filter, a typed address match and the paging over the loaded rows - reads the catalogue now in use, and records that were deleted or became inaccessible do not linger in it. A swap is not a change of authority and re-reads no whole-inventory search: the advanced reader's identity and page cache are the authorization scope and the submitted criteria, so a submitted advanced result keeps its windows and cached pages, and the person re-runs the search to read the database again. The generation retains its authorized count across promotion instead of recounting. A replacement that stops while authority remains intact keeps the working catalogue and its synchronization time exactly as they were, states the failure instead of a completed load and keeps its staged rows so Retry continues that traversal from its own cursor. An authorization refusal from a page, count or session check instead clears both generations and the scoped cache through the protected-session lifecycle; changed identity, role or access revision also clears them before a new protected load re-establishes access. One replacement runs at a time, a refresh of a catalogue that has not finished arriving is refused, and a response belonging to a superseded generation or to a scope that has since changed is discarded rather than folded in.

## Measured payload budget

Measured on production before this decision, from the captain's own numbers: the authorized inventory is 18,801 properties and 18,510 of them carry both an old and a current stored address. The full summary contract measures 12.5 MB of JSON held in browser memory, roughly 2.3 MB gzipped over the wire; address text alone is 9.5 MB and a display minimum without it is 6.2 MB.

At that measured rate one property's summary is about 665 bytes, so this read's bound of 200 summaries is about 133 KB of JSON and about 25 KB gzipped - the first page is affordable before anything else is built. The budget for the whole authorized catalogue is the measured 12.5 MB in memory and about 2.3 MB over the wire; a payload that exceeds it must be answered with an explicitly scoped catalogue or a server-search mode, never silent truncation, and the progressive loader that would reach that size has to be measured against this budget before it is relied on.

## Considered options

- Caching individual search strings - rejected: every spelling, abbreviation and partial address is a different key, so the cache buys almost no reuse, and each search still reads the database.
- Keeping server search and debouncing it - rejected: it is still a database read per search and per remount, which is the latency this change removes; the server search is kept only as the explicit full-inventory path.
- Reading the whole authorized inventory into the page at once - rejected: at the measured 12.5 MB it makes the first paint wait on the largest payload, and nothing is usable until it all arrives. This slice reads one bounded page and later work loads progressively.
- Prefetching the catalogue in the server-rendered shell - rejected: it duplicates the browser's own read, and it would put employee-specific inventory into a server-rendered response and any cache in front of it.
- A durable browser store (IndexedDB, service worker) - rejected for this release: persistent storage and offline access are out of scope, and a memory-only cache is discarded when the tab closes, which is the honest boundary.
- Cursor paging for the list stream - rejected earlier in [ADR 0002](0002-inventory-list-stream-and-table-view.md) and not reopened here: that decision is about a virtualised list with no pages. The catalogue is a different read with a different job - one stable traversal a loader can resume - so it carries a keyset cursor of its own.

## Consequences

- The catalogue answers the ordinary browse, the supported filters (status, listing mode, type, price and area), the free-text address and property-code match and the result paging in the browser, and issues no request for any of them ([#194](https://github.com/Leonard-Data/SGN-Inventory/issues/194)). A criterion the summary fields do not carry routes to an explicit advanced search of the whole inventory rather than being approximated locally: the province/ward and contact filters name catalog identities the summaries do not hold, and a chronological ordering is also the narrower `available`/`negotiating` database view rather than a reordering of the loaded rows. The filter panel states the split, keeps its advanced criteria until it is run, and the list says which of the two answered it; an advanced page is held under its own key - user scope, submitted criteria, ordering and page - with a bounded retention separate from the catalogue's.
- A typed search is filtered, not definitive: the list states how many of the loaded properties match and that these are the loaded properties. It never presents a partial catalogue as a search of the whole inventory, and the search button remains the full-inventory path until the catalogue is complete.
- The catalogue carries the summary fields the list already draws. Contacts, legal fields, notes and the entry chronology are deliberately absent: they belong to detail and chronological reads that authorize them separately. It carries the creator reference and the resolved creator display name, because the ordinary browse drew that attribution from the streamed read and a locally filtered list would otherwise lose it; each page resolves its own distinct creators in one `list_employee_names` read through the sanctioned projection, and a creator that does not resolve states nothing at all.
- Each address variant is searched independently using its recorded text and the house number, street, district and commune parts already carried by the summary, and the recorded property code is matched beside them - in full, which ranks above every address rank, and as a fragment at the loosest rank - because the database's own text predicate matches `property_code` as well as the address. The fields the summary does not carry (the province label and the picker-only official unit names that `search_text` also holds) cannot be matched in the browser: the local result states that it matched the fields the browser holds and the search button routes the query to the whole-inventory search, which does match them, and closing that gap remains with the matching slice (#191). The catalogue does not add `property_addresses.search_text`, which would duplicate address text against the measured payload budget.
- The summary shape is versioned (`CATALOGUE_SCHEMA_VERSION`). A later field change starts a new cache key rather than reading rows of the old shape as the new one, and an access-revision change does the same for authority.
- Retention is infinite for this one catalogue only while its authorized scope remains current; a scope change or loss of protected data drops the former entry. An unchanged scope keeps its page across client navigation and window refocus. Detail and advanced-search reads keep their own bounded retention, and memory caching cannot retract rows already delivered.
- This is the first slice of [#186](https://github.com/Leonard-Data/SGN-Inventory/issues/186) and deliberately the narrowest complete one. Progressive background loading with progress ([#189](https://github.com/Leonard-Data/SGN-Inventory/issues/189)), explicit Refresh as a replacement catalogue ([#190](https://github.com/Leonard-Data/SGN-Inventory/issues/190)), Vietnamese normalization and ranking ([#191](https://github.com/Leonard-Data/SGN-Inventory/issues/191)), navigation restoration ([#192](https://github.com/Leonard-Data/SGN-Inventory/issues/192)), mutation reconciliation ([#193](https://github.com/Leonard-Data/SGN-Inventory/issues/193)) and the flagged rollout ([#195](https://github.com/Leonard-Data/SGN-Inventory/issues/195)) are separate slices.

The endpoint's own contract is documented in [`docs/database-contract.md`](../database-contract.md); the local index and the read's projection are in `src/features/properties/catalogue.ts`, `catalogue-data.ts` and `address-index.ts`.
