+# Browser property catalogue and local address search
+
+Status: accepted (2026-10-20)
+
+Ordinary address search read the database. The list carried the free-text query in its address and every submitted search was a window of a server read (`stream_inventory`), so a remount or a return from a property's details read the same rows again. Salespeople search mostly by free text address, and caching individual search strings buys little: every spelling, abbreviation and partial address is a different key.
+
+We decided the browser holds a compact, user-scoped catalogue of the authorized inventory and searches it locally. An authenticated Route Handler, `GET /api/properties/catalogue`, answers one bounded page of property summaries in a stable property-identity order, with each property's stored address variants flattened into its own row and money and measurements cast to text. The read runs on the caller's own session client, so Row Level Security is what decides which rows and fields exist for them at all, and it is reapplied on every page: the cursor (`after`) is a position in that one ordering and never an authorization grant. Responses stay private and `no-store`. The shared protected-session lifecycle brackets the catalogue read with live session checks and owns publication, cancellation and refocus checks. TanStack Query deduplicates the read and holds the browser cache under one key per authorized context (employee identity and role, the server-maintained `accessRevision`, and the summary's own schema version), with `staleTime`/`gcTime` at infinity and no automatic query refetch. A changed scope removes the former entry; superseded responses are discarded, and consumers only accept a catalogue matching their own protected session. A local index folds each property's recorded addresses once per loaded page and keeps the original text for display; typing in the address box narrows those rows in the browser and issues no request, while submitting the box still runs the existing server search over the whole inventory.
+
+The loader and cache are mounted once in the shared authenticated layout, so the list and a property's details reuse one catalogue instead of each reading their own. The browser is the single initial loading owner: the list's server-rendered shell reads no catalogue at all, so nothing is fetched twice and no employee-specific result passes through a shared cache. The catalogue is a browsing snapshot. Locking, approvals and edits always validate against current server state, and a locally filtered list states what it is - the loaded catalogue, never the whole inventory.
+
+## Measured payload budget
+
+Measured on production before this decision, from the captain's own numbers: the authorized inventory is 18,801 properties and 18,510 of them carry both an old and a current stored address. The full summary contract measures 12.5 MB of JSON held in browser memory, roughly 2.3 MB gzipped over the wire; address text alone is 9.5 MB and a display minimum without it is 6.2 MB.
+
+At that measured rate one property's summary is about 665 bytes, so this read's bound of 200 summaries is about 133 KB of JSON and about 25 KB gzipped - the first page is affordable before anything else is built. The budget for the whole authorized catalogue is the measured 12.5 MB in memory and about 2.3 MB over the wire; a payload that exceeds it must be answered with an explicitly scoped catalogue or a server-search mode, never silent truncation, and the progressive loader that would reach that size has to be measured against this budget before it is relied on.
+
+## Considered options
+
+- Caching individual search strings - rejected: every spelling, abbreviation and partial address is a different key, so the cache buys almost no reuse, and each search still reads the database.
+- Keeping server search and debouncing it - rejected: it is still a database read per search and per remount, which is the latency this change removes; the server search is kept only as the explicit full-inventory path.
+- Reading the whole authorized inventory into the page at once - rejected: at the measured 12.5 MB it makes the first paint wait on the largest payload, and nothing is usable until it all arrives. This slice reads one bounded page and later work loads progressively.
+- Prefetching the catalogue in the server-rendered shell - rejected: it duplicates the browser's own read, and it would put employee-specific inventory into a server-rendered response and any cache in front of it.
+- A durable browser store (IndexedDB, service worker) - rejected for this release: persistent storage and offline access are out of scope, and a memory-only cache is discarded when the tab closes, which is the honest boundary.
+- Cursor paging for the list stream - rejected earlier in [ADR 0002](0002-inventory-list-stream-and-table-view.md) and not reopened here: that decision is about a virtualised list with no pages. The catalogue is a different read with a different job - one stable traversal a loader can resume - so it carries a keyset cursor of its own.
+
+## Consequences
+
+- Local filtering is offered for the ordinary browse only. A chronological ordering or a filter set names a result set the loaded page cannot state, so those keep the server search; the local-filter and advanced-search split is a later slice ([#194](https://github.com/Leonard-Data/SGN-Inventory/issues/194)).
+- A typed search is filtered, not definitive: the list states how many of the loaded properties match and that these are the loaded properties. It never presents a partial catalogue as a search of the whole inventory, and the search button remains the full-inventory path until the catalogue is complete.
+- The catalogue carries the summary fields the list already draws. Contacts, legal fields, notes, the creator and the entry chronology are deliberately absent: they belong to detail and chronological reads that authorize them separately, and the creator would cost a further read per page.
+- Each address variant is searched independently using its recorded text and the house number, street, district and commune parts already carried by the summary. Picker-only official unit names are not carried, so they remain a local-search gap for the matching slice (#191); full-inventory server search still includes them. The catalogue does not add `property_addresses.search_text`, which would duplicate address text against the measured payload budget.
+- The summary shape is versioned (`CATALOGUE_SCHEMA_VERSION`). A later field change starts a new cache key rather than reading rows of the old shape as the new one, and an access-revision change does the same for authority.
+- Retention is infinite for this one catalogue only while its authorized scope remains current; a scope change or loss of protected data drops the former entry. An unchanged scope keeps its page across client navigation and window refocus. Detail and advanced-search reads keep their own bounded retention, and memory caching cannot retract rows already delivered.
+- This is the first slice of [#186](https://github.com/Leonard-Data/SGN-Inventory/issues/186) and deliberately the narrowest complete one. Progressive background loading with progress, explicit Refresh as a replacement catalogue, Vietnamese normalization and ranking, navigation restoration, mutation reconciliation, the local-filter split and the flagged rollout are separate slices ([#189](https://github.com/Leonard-Data/SGN-Inventory/issues/189)-[#195](https://github.com/Leonard-Data/SGN-Inventory/issues/195)).
+
+The endpoint's own contract is documented in [`docs/database-contract.md`](../database-contract.md); the local index and the read's projection are in `src/features/properties/catalogue.ts`, `catalogue-data.ts` and `address-index.ts`.

+// The local address index: the catalogue's recorded addresses folded once per property, and the
+// one match the address box runs while a person types. Folding is the accent-insensitive
+// comparison the database's own address search already documents, kept here so a keystroke reads
+// nothing at all. Ranking, abbreviation expansion, house-number structure and the rules that
+// relate an old address to a current one belong to the matching slice (issue #191) and are
+// deliberately not here.
+import type { PropertySummary } from './types';
+
+export type CatalogueAddressVariant = {
+  // The recorded format the variant was stored in: legacy, current or alternate.
+  format: string;
+  // The recorded address text exactly as entered. Display reads this, never the folded form.
+  addressText: string;
+  folded: string;
+};
+
+export type CatalogueIndexEntry = {
+  record: PropertySummary;
+  variants: CatalogueAddressVariant[];
+};
+
+export function localAddressQuery(
+  typed: string,
+  edited: boolean,
+  sort: string | null,
+  filters: number,
+): string | null {
+  if (!edited || sort !== null || filters > 0) return null;
+  return typed.trim();
+}
+
+// The comparison form of an address: case-folded, without accent marks, with đ read as d, and with
+// repeated whitespace collapsed. House-number structure (12/5, 12A) survives untouched, and
+// nothing is added to the text: an unrecorded new ward name is never inferred from an old one.
+export function foldAddress(text: string): string {
+  return text
+    .toLowerCase()
+    .normalize('NFD')
+    .replace(/[\u0300-\u036f]/g, '')
+    .replaceAll('đ', 'd')
+    .replace(/\s+/g, ' ')
+    .trim();
+}
+
+// The index is built once per loaded page rather than once per keystroke: every property's variants
+// are folded here, and the record itself is kept so a result draws its recorded address text.
+export function buildAddressIndex(
+  records: readonly PropertySummary[],
+): CatalogueIndexEntry[] {
+  return records.map((record) => ({
+    record,
+    variants: record.addresses.map((address) => ({
+      format: address.format,
+      addressText: address.addressText,
+      folded: foldAddress(
+        [
+          address.addressText,
+          address.houseNumber,
+          address.street,
+          address.district,
+          address.commune,
+        ].join(' '),
+      ),
+    })),
+  }));
+}
+
+// The properties whose recorded address text matches what the person typed. Each stored variant is
+// searched on its own, so a query can never match a mixture of an old district and a current ward,
+// and a property matches when any one of its variants does. An empty query is the whole loaded
+// page, never an empty result.
+export function matchCatalogue(
+  index: readonly CatalogueIndexEntry[],
+  query: string,
+): PropertySummary[] {
+  const folded = foldAddress(query);
+  if (!folded) return index.map((entry) => entry.record);
+  return index
+    .filter((entry) =>
+      entry.variants.some((variant) => variant.folded.includes(folded)),
+    )
+    .map((entry) => entry.record);
+}

+  CATALOGUE_PAGE_SIZE,
+  CATALOGUE_SELECT,
+  catalogueFailure,

+import type { CataloguePage } from './types';
+
+// One page of the browser catalogue: the caller's own authorized, unarchived inventory in one
+// stable identity order, with each property's address variants flattened into its row.
+//
+// The cursor names the position the page starts after and nothing else. The read runs on the
+// caller's own session client, so row level security is what decides which rows exist for them at
+// all, and it is reapplied on every page: a cursor can never reach a row the caller may not read.
+export async function cataloguePage(
+  context: RouteContext,
+  after: string | null,
+): Promise<CataloguePage> {
+  const read = context.client
+    .from('properties')
+    .select(CATALOGUE_SELECT)
+    // The ordinary inventory boundary: an archived record is not part of the browsing catalogue,
+    // exactly as the list's own stream excludes it.
+    .is('archived_at', null)
+    .order('id', { ascending: true })
+    .limit(CATALOGUE_PAGE_SIZE);
+  const { data, error } = await (after === null ? read : read.gt('id', after));
+  if (error) {
+    const failure = catalogueFailure(error.code);
+    throw new ApiError(failure.status, failure.code);
+  }
+  const rows = (data ?? []) as unknown as CatalogueRow[];
+  return {
+    properties: rows.map(catalogueSummary),
+    nextCursor: nextCatalogueCursor(rows.map((row) => row.id)),
+  };

+// load behind it. Nothing here authorizes anything - a lock, an approval or an edit always
+// validates against current server state, never against this browsing snapshot.
+export type CatalogueState = {
+  status: 'loading' | 'ready' | 'failed';
+  index: readonly CatalogueIndexEntry[];
+  loadedCount: number;
+  scope: EmployeeSession | null;
+};
+
+const EMPTY: CatalogueState = {
+  status: 'loading',
+  index: [],
+  loadedCount: 0,
+  scope: null,
+};
+const CatalogueContext = createContext<CatalogueState>(EMPTY);
+
+export function useCatalogue(session: EmployeeSession | null): CatalogueState {
+  const catalogue = useContext(CatalogueContext);
+  if (
+    catalogue.scope &&
+    (!session ||
+      sessionDiffers(
+        renderedSession(catalogue.scope.employee),
+        catalogue.scope.accessRevision,
+        session,
+      ))
+  )
+    return EMPTY;
+  return catalogue;
+}
+
+export function CatalogueProvider({ children }: { children: ReactNode }) {
+  // One client for the whole authenticated application, created once per browser session: the
+  // catalogue outlives every route inside the shell, and a page reload is what starts it over.
+  const [queryClient] = useState(
+    () => new QueryClient({ defaultOptions: { queries: { retry: false } } }),
+  );
+  return (
+    <QueryClientProvider client={queryClient}>
+      <CatalogueLoader>{children}</CatalogueLoader>
+    </QueryClientProvider>
+  );
+}
+
+function CatalogueLoader({ children }: { children: ReactNode }) {
+  const queryClient = useQueryClient();
+  const read = useCallback(
+    (signal: AbortSignal, scope: EmployeeSession) =>
+      readCatalogue(queryClient, signal, scope),
+    [queryClient],
+  );
+  const { data, busy, error } = useProtectedData<ScopedCatalogue>(read);
+  useEffect(() => {
+    if (!busy && !data) queryClient.clear();
+  }, [busy, data, queryClient]);
+  const snapshot = busy ? null : data;
+  const page = snapshot?.page ?? null;
+  const index = useMemo(
+    () => buildAddressIndex(page?.properties ?? []),
+    [page],
+  );
+  const state = useMemo<CatalogueState>(
+    () => ({
+      status: error ? 'failed' : snapshot ? 'ready' : 'loading',
+      index,
+      loadedCount: index.length,
+      scope: snapshot?.scope ?? null,
+    }),
+    [error, snapshot, index],
+  );
+  return (
+    <CatalogueContext.Provider value={state}>
+      {children}
+    </CatalogueContext.Provider>
+  );

+export function localStreamWindows<T>(
+  rows: readonly T[],
+): ReadonlyMap<number, T[]> {
+  const windows = new Map<number, T[]>();
+  for (let offset = 0; offset < rows.length; offset += STREAM_PAGE_SIZE)
+    windows.set(offset, rows.slice(offset, offset + STREAM_PAGE_SIZE));
+  return windows;
